# app-registry — delta

## MODIFIED Requirements

### Requirement: Pinned listing base (Phase 1, no plugin)

A Store definition MAY carry a second proxy entry named
`catalog-apps` declaring the listing base: a pinned tag
base (`https://raw.githubusercontent.com/<owner>/<repo>/
<tag>/catalog/`). The shell SHALL route management calls
by target: a Store self-update uses the discovery base
(`catalog` entry, `main`); every other app's rows,
install, and update use the listing base when present,
falling back to the discovery base when absent. An
explicit `catalogBase` supplied to the agent exports
SHALL still win over both. Changing either proxy URL
SHALL bump the Store's `catalogVersion` by 1 under the
existing rule. This requirement is Phase 1 and is NOT
gated behind the plugins spec.

**Amendment (catalog-tags-semver-line):** the pinned tag
SHALL be the semver line, bare `<major>.<minor>` (for
example `4.2`): no patch, no `v` prefix. A line tag MAY
be moved, only across commits compatible with that line
(no app requiring a newer shell, no schema beyond the
line's floor, manifest validates). An app add SHALL be
visible to the Store after the line tag moves, with no
pin move and no Store update. When the shell line
advances (a minor or major change), the old line's tag
SHALL stop moving (frozen) and the pin SHALL move to
the new line's tag through a Store update gated by
`minPackageVersion`. The "tags SHALL NOT be moved after
cutting" rule from compatible-catalog is superseded by
this amendment for line tags.

#### Scenario: App add visible after a tag move, no Store update
- **WHEN** a new app is pushed to `main` and the `4.2`
  line tag is moved to that commit
- **THEN** a Store pinned to the `4.2` base lists the new
  app with no pin move and no Store update.

#### Scenario: Shell-line advance freezes the old tag
- **WHEN** the shell line advances to `4.3` and the pin
  moves to the `4.3` tag in a new Store version
- **THEN** a shell on the `4.2` line keeps listing from
  the frozen `4.2` tag until its shell is updated, and
  the new Store version is not offered to it.

### Requirement: Releases index (Phase 2, plugin-gated)

`catalog/releases.json` SHALL list the catalog snapshots, one
entry per release tag: `{ version, tag, sha, shellVersion }`,
sorted deterministically. It SHALL be generated by extending
`scripts/build-catalog-index.ts` (the same run that
regenerates `catalog/catalog.json`), and SHALL never be
hand-edited. For each local git tag, the generator SHALL
verify it against the tag itself: `git show
<tag>:pkg/package.json` parses and its version matches the
tag name, and `git show <tag>:catalog/catalog.json` exists
and parses. A tag failing those checks SHALL fail the
generator loudly, not be skipped silently. The harness
SHALL fail on a stale `releases.json`: any local tag
missing from it, any entry pointing at a missing tag or a
mismatched SHA, any entry whose `shellVersion` does not
match the version at that tag, or non-deterministic
ordering. Tags SHALL NOT be moved after cutting.

**Amendment (catalog-tags-semver-line):** the "Tags SHALL
NOT be moved after cutting" sentence is superseded by the
line-tag rule (see "Pinned listing base" above): line tags
move within their line. The generator's "version matches
the tag name" check assumes full-version tags; a line tag
(`4.2`) has no full version to match, so that check needs
a line-aware form before Phase 2 lands. That is a Phase 2
follow-up recorded in this change's design, not a change
to this requirement now.
