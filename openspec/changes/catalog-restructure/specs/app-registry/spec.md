# Spec Delta

## ADDED Requirements

### Requirement: Catalog index

The package SHALL ship a generated catalog index at
`pkg/catalog/catalog.json`, listing every catalog app sorted by id. Each
entry SHALL carry: id, label, catalogVersion, fingerprint, installMode,
definitionPath, recipePath. definitionPath and recipePath are relative to
`pkg/catalog/` (for example `app-store/definition.json`,
`app-store/RECIPE.md`). The index SHALL also carry a `collections` section (proposed name)
listing collection recipes: each entry SHALL carry id, recipePath, and
the apps it installs in order (for example id `starter`, recipePath
`collections/starter/RECIPE.md`, apps `["app-store", "help", "about"]`).
A collection entry has no definition, fingerprint, or catalogVersion.
The index SHALL be generated by
`scripts/build-catalog-index.ts` from the app directories, never
hand-written; the generator SHALL compute each fingerprint with the
existing `fingerprintDefinition` and SHALL read installMode from the
definition (absent means `json`). Regenerating the index from unchanged
definitions SHALL produce byte-identical output. The catalog harness
SHALL fail if the index does not match the directories and the definitions
(ids, alphabetical order, catalogVersions, fingerprints, install modes),
or if the `collections` section does not match the collections
directories.

#### Scenario: Index lists every app once, sorted
- **WHEN** the generator runs over the app directories
- **THEN** `pkg/catalog/catalog.json` has one entry per app directory, sorted by id, each with id, label, catalogVersion, fingerprint, installMode, definitionPath, and recipePath.

#### Scenario: Generator is idempotent
- **WHEN** the generator runs twice over unchanged definitions
- **THEN** both outputs are byte-identical.

#### Scenario: Stale index fails the harness
- **WHEN** a definition changes without re-running the generator (or an app directory is added without an index entry)
- **THEN** the catalog harness reports the index mismatch and fails.

#### Scenario: Index lists collection recipes
- **WHEN** the generator runs over the collections directories
- **THEN** the index has a `collections` section with one entry per collection, each with id, recipePath, and apps.

### Requirement: App recipe

Each catalog app SHALL ship a `RECIPE.md` beside its `definition.json` in
`pkg/catalog/<id>/`. A recipe is a procedure made of steps: each install
step names exactly one app, and one recipe MAY install any number of apps
by naming one install step per app. Steps after install MAY ask the user
for input, fetch data, or set app state. The default recipe is trivial:
install the sibling `definition.json` via
`install_from_catalog('<id>')`, then verify with `list_apps`. A
non-trivial recipe SHALL exist only where the app genuinely needs setup
beyond install. An app's own recipe covers that app alone: the App Store
recipe installs `app-store` and verifies it with `list_apps`. Help and
About are unattended JSON installs with no new property. A recipe that
installs several apps is a collection recipe (see Collection recipe),
not an app recipe.

#### Scenario: Every app directory has a recipe
- **WHEN** the catalog directories are listed
- **THEN** each `<id>/` contains `definition.json` and `RECIPE.md`.

#### Scenario: Trivial recipe installs and verifies
- **WHEN** an agent follows a trivial recipe
- **THEN** the app is installed from its sibling `definition.json` and appears in `list_apps()`.

#### Scenario: An app recipe installs its own app alone
- **WHEN** an agent follows the App Store recipe
- **THEN** `app-store` is installed and verified with `list_apps()`, and no other app is installed.

### Requirement: Collection recipe

A collection recipe is a standalone recipe that installs a set of apps
together. It is NOT an app: it has no definition, no fingerprint, and no
catalogVersion. Its proposed home is `pkg/catalog/collections/<name>/RECIPE.md`
(proposed; the user may correct the home in review), and the first
collection is proposed id `starter` (proposed; the user may correct the id
in review). The starter collection recipe installs `app-store`, `help`,
and `about` (one `install_from_catalog` step per app, in that order), then
verifies all three with `list_apps`. The catalog index SHALL list
collection recipes in a `collections` section (see Catalog index). The
empty-state "Install the App Store" prompt points at the collection
recipe, not at the app-store's own recipe.

#### Scenario: One collection recipe installs several apps
- **WHEN** an agent follows the starter collection recipe
- **THEN** `app-store`, `help`, and `about` are each installed by their own install step, and all three are verified with `list_apps()`.

#### Scenario: A collection recipe is not an app
- **WHEN** the catalog is listed
- **THEN** the starter collection appears in the index `collections` section only, with no definition, fingerprint, or catalogVersion, and does not appear in the app listing.

### Requirement: Recipe install mode

A catalog definition MAY carry `installMode`: `"json"`, `"recipe-only"`,
or `"recipe-or-json"`. Absent means `"json"` — unattended install from
the JSON alone. `"recipe-only"` means the app MUST be installed via its
recipe: it still appears in the App Store list, but the Store shows the
recipe prompt (selectable text for the user to supply to their agent) in
place of one-tap install. `"recipe-or-json"` means the app has a
non-trivial recipe for full configuration AND can be installed unattended
from JSON: in the Store it installs without the prompt message (one-tap
install works); it lands unconfigured and the app's built-in empty-state
prompt guides setup, while the recipe fully configures it at install
time. Only an app with a non-trivial recipe SHALL carry `installMode`;
most definitions SHALL carry no such property. A definition with
`installMode` present SHALL fail validation unless the value is `"json"`,
`"recipe-only"`, or `"recipe-or-json"`. The canonical stored definition
SHALL preserve `installMode` through `add_app` normalization, and
`installMode` SHALL be excluded from the definition fingerprint, exactly
like `catalogVersion`, so adding it SHALL NOT change any installed app's
fingerprint, snapshot, or update status.

#### Scenario: Unattended install is the default
- **WHEN** a catalog definition carries no `installMode`
- **THEN** it installs from the JSON alone with no recipe step, and its listing reports install mode `json`.

#### Scenario: Recipe-only app declares its mode
- **WHEN** a catalog definition carries `"installMode": "recipe-only"`
- **THEN** it validates, its stored definition preserves the field, its listing reports install mode `recipe-only`, and the Store lists it with the recipe prompt in place of one-tap install.

#### Scenario: Recipe-or-json app declares its mode and installs unattended
- **WHEN** a catalog definition carries `"installMode": "recipe-or-json"`
- **THEN** it validates, its stored definition preserves the field, its listing reports install mode `recipe-or-json`, and it installs unattended from the JSON alone without the prompt message, landing unconfigured with its built-in empty-state prompt guiding setup.

#### Scenario: No app is recipe-only today
- **WHEN** the catalog is listed
- **THEN** no entry reports install mode `recipe-only`; `app-store`, `daily-feed`, and `generic-feed` report `recipe-or-json` and the other 17 report `json`.

#### Scenario: Invalid install mode fails validation
- **WHEN** a definition carries an `installMode` other than `"json"`, `"recipe-only"`, or `"recipe-or-json"`
- **THEN** validation rejects it.

#### Scenario: installMode does not change fingerprints
- **WHEN** the fingerprint of an app's definition is computed with and without its `installMode` field
- **THEN** the two fingerprints are identical, and no installed copy of the app changes update status.

## MODIFIED Requirements

### Requirement: Shipped catalog

The package SHALL ship a catalog: every
`pkg/catalog/<id>/definition.json` file is an app definition the user can
install from the browser, and every `pkg/catalog/<id>/` directory also
carries a `RECIPE.md` (see App recipe). The catalog SHALL be enumerated
by an explicit import list in package code (alphabetical by id), not by
runtime directory listing; a directory in `pkg/catalog/` without an
import entry SHALL NOT be listed. The listing summaries SHALL be driven
by the generated index at `pkg/catalog/catalog.json` (see Catalog index);
the full definitions SHALL still be statically imported for install.
Every catalog definition SHALL validate through `validateDefinition` and
install through `add_app`, satisfying the bundle manifest shape (entry
`index.html`, relative `.html`/`.js`/`.css` only, within the 256 KiB cap)
and the 16 MiB storage budget. Catalog definitions are publisher-shipped
and trusted like any `add_app` definition: installing one trusts its
bundle code, which runs same-origin with session authority.

#### Scenario: Every catalog file validates and installs
- **WHEN** each `definition.json` in `pkg/catalog/<id>/` is submitted to `add_app` in a blank store
- **THEN** each returns `{ ok: true, id }` and appears in `list_apps()`.

#### Scenario: Unimported file is not listed
- **WHEN** an app directory exists in `pkg/catalog/` with no import-list entry
- **THEN** the App Store listing omits it.

#### Scenario: Catalog listing order is deterministic
- **WHEN** the catalog is listed
- **THEN** entries appear in import-list order (alphabetical by id).

### Requirement: Catalog version

Every catalog definition SHALL carry `catalogVersion`: a positive
integer, starting at 1 on that app's first versioned release, incremented
by exactly 1 on any change to that app's definition file, never reused,
never decreased, and never bumped for an unrelated app or a shell change.
`catalogVersion` is distinct from `schemaVersion` (definition format era)
and from the shell's package version. A catalog definition without a
valid `catalogVersion` SHALL fail catalog validation. The canonical
stored definition SHALL preserve `catalogVersion` through `add_app`
normalization. Adding `installMode` to a definition SHALL NOT require a
`catalogVersion` bump: the field is excluded from the definition
fingerprint, so it cannot change any installed app's update status (see
Recipe install mode).

#### Scenario: Catalog definition carries a version
- **WHEN** a catalog definition is validated
- **THEN** it is rejected if `catalogVersion` is missing, non-integer, or less than 1.

#### Scenario: Installed copy keeps its catalog version
- **WHEN** a catalog app is installed through `add_app`
- **THEN** the stored definition carries the catalog definition's `catalogVersion`.

#### Scenario: Adding installMode needs no version bump
- **WHEN** `"installMode": "recipe-only"` is added to a catalog definition with no other change
- **THEN** its `catalogVersion` stays the same, its fingerprint is unchanged, and no installed copy is marked as needing an update.
