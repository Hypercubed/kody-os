# app-registry — delta

## MODIFIED Requirements

### Requirement: Store follows the latest catalog

The App Store's declared catalog base SHALL be the `main` branch
catalog base
(`https://raw.githubusercontent.com/Hypercubed/kody-os/main/catalog/`),
so the Store follows the latest catalog (the latest commit) and can
discover its own updates. A fixed release tag SHALL NOT be the
Store's declared base: a Store pinned to a tag only ever sees that
tag's catalog, where the Store is itself, and can never discover a
newer catalog or a newer Store.

**Amendment (compatible-catalog, Phase 1):** the declared base is now the
*discovery* base, not necessarily the listing/install base. The
Store declares a second proxy entry, `catalog-apps`, whose URL
is the *listing* base: a pinned tag
(`https://raw.githubusercontent.com/Hypercubed/kody-os/<tag>/
catalog/`). The Store's rows and installs come from that
listing base when the installed Store declares one, and from
the declared (`main`) base when it declares none. The Store's
own update comes from the discovery base and SHALL be gated
by `minPackageVersion`: when the new Store version requires
a newer shell than the one running, the update SHALL be
refused, the same as any other app.

**Amendment (compatible-catalog, Phase 2):** when a
catalog-resolver plugin is installed (see the shell delta for
the plugin interface, gated behind the plugins spec), the
Store's rows and installs come from the *resolved* catalog
snapshot (see "Compatible catalog resolution" below) instead
of the pinned listing base, and the Store displays the
resolved snapshot instead of the pinned tag.

#### Scenario: Store sees its own update
- **WHEN** the catalog at `main` holds a Store definition newer
  than the installed Store, and the running shell meets that
  definition's `minPackageVersion`
- **THEN** the Store offers its own update.

#### Scenario: Store update refused when shell is too old
- **WHEN** the catalog at `main` holds a Store definition whose
  `minPackageVersion` is above the running shell
- **THEN** the Store update is refused with the required and running
  versions named.

#### Scenario: Fixed tag does not freeze the Store
- **WHEN** the App Store's declared catalog base is read
- **THEN** it is the `main` branch base, not a fixed release tag.

#### Scenario: Pinned listing base is the listing base in Phase 1
- **WHEN** the installed Store declares a `catalog-apps` entry
  pinned to tag `v4.1.9`
- **THEN** the Store lists and installs apps other than itself
  from the `v4.1.9` snapshot's base, and its own update comes
  from `main`.

#### Scenario: Resolved snapshot is the listing base when the plugin is installed
- **WHEN** a resolver plugin is installed and resolves snapshot
  `v4.1.9` for a shell running `4.1.9`
- **THEN** the Store lists and installs from the `v4.1.9`
  snapshot's base, not from the pinned listing base, and displays that snapshot.

#### Scenario: No listing entry means main, as before
- **WHEN** the installed Store declares no `catalog-apps` entry
  and no resolver plugin is installed
- **THEN** the Store lists and installs from the declared
  (`main`) base, and displays it, exactly as before this change.

## ADDED Requirements

### Requirement: Pinned listing base (Phase 1, no plugin)

A Store definition MAY carry a second proxy entry named
`catalog-apps` declaring the listing base: a pinned tag
base (`https://raw.githubusercontent.com/<owner>/<repo>/
<tag>/catalog/`). The shell SHALL route management calls
by target: a Store self-update uses the discovery base
(`catalog` entry, `main`); every other app's rows,
install, and update use the listing base when present,
falling back to the discovery base when absent. An
explicit `catalogBase` supplied to the agent exports
SHALL still win over both. Changing either proxy URL
SHALL bump the Store's `catalogVersion` by 1 under the
existing rule. This requirement is Phase 1 and is NOT
gated behind the plugins spec.

#### Scenario: Listing base pins app installs
- **WHEN** the installed Store declares `catalog-apps`
  pinned to `v4.1.9`
- **THEN** installing an app other than `app-store`
  fetches its definition from the `v4.1.9` base.

#### Scenario: Store self-update uses the discovery base
- **WHEN** the installed Store declares `catalog-apps`
  pinned to `v4.1.9`
- **THEN** updating `app-store` itself fetches its
  definition from `main`, not from `v4.1.9`.

### Requirement: Releases index (Phase 2, plugin-gated)

`catalog/releases.json` SHALL list the catalog snapshots, one
entry per release tag: `{ version, tag, sha, shellVersion }`,
sorted deterministically. It SHALL be generated by extending
`scripts/build-catalog-index.ts` (the same run that
regenerates `catalog/catalog.json`), and SHALL never be
hand-edited. For each local git tag, the generator SHALL
verify it against the tag itself: `git show
<tag>:pkg/package.json` parses and its version matches the
tag name, and `git show <tag>:catalog/catalog.json` exists
and parses. A tag failing those checks SHALL fail the
generator loudly, not be skipped silently. The harness
SHALL fail on a stale `releases.json`: any local tag
missing from it, any entry pointing at a missing tag or a
mismatched SHA, any entry whose `shellVersion` does not
match the version at that tag, or non-deterministic
ordering. Tags SHALL NOT be moved after cutting.

#### Scenario: Generator lists a new tag
- **WHEN** a tag `v4.1.9` is cut and the generator is re-run
- **THEN** `releases.json` gains an entry for `v4.1.9` with
  the tag's commit SHA and `shellVersion` `4.1.9`.

#### Scenario: Mismatched tag fails the generator
- **WHEN** a tag's `pkg/package.json` version does not match
  the tag name
- **THEN** the generator fails loudly and writes nothing.

#### Scenario: Stale index fails the harness
- **WHEN** a local tag is missing from `releases.json`, or
  an entry's SHA does not match its tag
- **THEN** the catalog harness fails.

### Requirement: Compatible catalog resolution (Phase 2, plugin-gated)

When a catalog-resolver plugin is installed, the resolver
SHALL read `catalog/releases.json` from `main` (HTTPS-only,
8000 ms timeout, size caps per the catalog fetch
discipline) and SHALL pick the highest entry whose
`shellVersion` is at or below the running shell version
(`getRunningPackageVersion`). Malformed entries and ties
SHALL be skipped, never picked. The resolver SHALL fetch
the manifest and definitions from that entry's SHA base
(`https://raw.githubusercontent.com/<owner>/<repo>/<sha>/
catalog/`), never from a bare tag name it has not
verified. If no entry qualifies, the resolver SHALL
report no compatible catalog and SHALL NOT fall through
to `main`. The per-app gates remain as a backstop: an app
in the resolved snapshot whose `minPackageVersion` is
above the running shell, or whose `schemaVersion` is
below `MIN_SUPPORTED_SCHEMA_VERSION`, SHALL still be
refused by `add_app` and shown gated in the Store. The
resolver SHALL NOT keep multiple versions of an app and
SHALL NOT pick a highest compatible version per app: the
snapshot is the unit of compatibility, and the catalog
still lists one version per app — the version in the
resolved snapshot.

#### Scenario: Resolver picks the highest compatible snapshot
- **WHEN** a shell runs `4.1.9` and `releases.json` lists
  snapshots for `4.1.8`, `4.1.9`, and `4.1.11`
- **THEN** the resolver picks `4.1.9` and fetches from its
  SHA base.

#### Scenario: No compatible snapshot reports none, not main
- **WHEN** a shell runs a version older than every entry
  in `releases.json`
- **THEN** the resolver reports no compatible catalog and
  does not fall through to `main`.

#### Scenario: Per-app gates still police the resolved snapshot
- **WHEN** an app in the resolved snapshot carries a
  `minPackageVersion` above the running shell
- **THEN** `add_app` refuses it with nothing written, and
  its Store row shows the requirement instead of an
  install control.

### Requirement: Durable last-good snapshot of the resolved catalog (Phase 2, plugin-gated)

The resolver SHALL keep one durable snapshot of the
resolved catalog in `packageStorage`, under the key the
plugins spec's storage-namespace rule assigns. The
snapshot holds the manifest plus the definitions as
fetched from the resolved snapshot. It SHALL be refreshed
only on a validated successful read from the resolved
snapshot; it SHALL NOT be refreshed with a gated or
invalid catalog, or with a catalog from a different
snapshot. On a fetch or validation failure of the
resolved snapshot, the resolver SHALL serve the durable
snapshot labelled stale (tag and age), and installs from
it SHALL proceed. If there is no durable snapshot, the
Store SHALL fall back to installed-only with an honest
error, as today.

#### Scenario: Failed read serves the stale snapshot
- **WHEN** the resolved snapshot fetch fails and a durable
  snapshot for that snapshot exists
- **THEN** the Store lists and installs from the durable
  snapshot, labelled stale with its tag and age.

#### Scenario: Gated read does not refresh the snapshot
- **WHEN** a read returns a catalog whose apps are gated
  for the running shell
- **THEN** the durable snapshot is left untouched.

#### Scenario: No snapshot means installed-only
- **WHEN** the resolved snapshot fetch fails and no
  durable snapshot exists
- **THEN** the Store shows installed apps only, with an
  honest error and retry.
