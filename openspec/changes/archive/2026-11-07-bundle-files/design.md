# Design: Bundle files on disk

## Context

A definition today is `bundle: { entry: "index.html", files: { "index.html": "<one giant escaped string>" } }`.
Verified Nov 6, 2026: the counter's whole UI (markup, `<style>`,
`<script>`) is a single JSON string; 17 of the 18 catalog apps carry
exactly one file (`index.html`); only the App Store carries more
(`index.html`, `store.js` 10914 bytes, `store.css` 1716 bytes), and it
already references them explicitly from its entry.

The serve-time inliner already exists (`pkg/src/apps/client.ts`):
`inlineBundleAssets` replaces `<script src="app.js"></script>` with an
inline `<script>` and `<link rel="stylesheet" href="style.css">` with an
inline `<style>`, reading the content from `bundle.files`; a reference
with no matching bundle file is dropped, never fetched; absolute URLs
are left untouched. `renderBundleContent` inlines the referenced assets
and appends any unreferenced `.js`/`.css` files as inline blocks; extra
`.html` files are ignored.

Install is static-import, not fetch: `install_from_catalog`
(`pkg/src/apps/registry.ts:1693`) and `update_from_catalog`
(`registry.ts:1711`) call `get_catalog_definition`, which returns a
statically imported definition from `pkg/src/apps/catalog.ts`. There is
no fetch path for catalog definitions anywhere in the code, and the
canonical "Shipped catalog" requirement states the full definitions
"SHALL still be statically imported for install". The Worker has no
directory listing at runtime; the bundler inlines what is imported
(`pkg/src/app.ts:144`, `package.json` and `settings.json` via
`import(..., { with: { type: "json" } })`). No text imports exist in
`pkg/src/` today.

The fingerprint hashes the canonical definition minus `catalogVersion`
and `installMode` (`registry.ts`, `fingerprintDefinition`); the catalog
index (`pkg/catalog/catalog.json`, generated by
`scripts/build-catalog-index.ts`) records `definitionPath` and
`recipePath` per app and computes each fingerprint from the definition.
The catalog harness (`tests/catalog-harness.ts`) checks the directories,
the index, and that every definition validates and installs.

## Decisions

### Decision 1 — The HTML explicitly references the other files; the loader inlines at serve time

Decided by the parent, Nov 6, 2026. The entry HTML carries standard
`<link rel="stylesheet" href="styles.css">` and
`<script src="app.js"></script>` references; the loader resolves them
by inlining at serve time, so the served document remains a single
self-contained HTML document.

Reasons: it is the web-native pattern; placement and order are explicit
and author-controlled (the author decides where the script and style
land, not the loader); the loader's job stays narrow (resolve + inline);
the served output is unchanged in kind from today's inlined
`index.html`, preserving the Scribe / no-external-resources model; and
it avoids loader magic (auto-injection order and placement) that would
need its own spec and edge cases.

This formalizes behavior that already exists: the inliner in
`client.ts` and the App Store's explicit references are the precedent.
No new serve-time mechanism is invented; the change makes the reference
contract explicit and enforced by validation (Decision 6).

### Decision 2 — Flat on-disk layout

Each app directory holds `definition.json` + `index.html` (required) +
optional `.js` / `.css` files, flat next to `definition.json` and
`RECIPE.md`. File names are free — any valid bundle path; the brief's
`app.js` / `styles.css` are examples, not mandated names (the App Store
already uses `store.js` / `store.css`).

Checked against the code: `isBundlePath` (`registry.ts:108`) allows up
to two path segments (one subdirectory level), so a flat layout (one
segment) is within the allowance — there is no conflict with the
one-level nesting rule. Flat is chosen for simplicity: one directory to
list, no subdirectories to enumerate, and the manifest is a plain list.

### Decision 3 — The manifest form; the runtime form is unchanged

`definition.json`'s `bundle` becomes `{ entry: "index.html", files: [...] }`,
a list of paths, instead of carrying file contents inline. The loader
assembles the runtime files map (`Record<path, content>`) from disk.

The runtime, canonical, and stored forms stay the inline files map, so
`validateDefinition`, `canonicalizeDefinition`, `fingerprintDefinition`,
`add_app`, install snapshots, and update detection are unchanged. The
inline form (`files` as a map of contents) stays valid — it remains the
transport form for `add_app` (an agent can only pass JSON) and the
stored form for installed apps. The two forms are distinguished by
`Array.isArray(files)`; a definition carrying both a list and a map is
an error (ambiguous).

### Decision 4 — Assembly: static text imports, with a generator fallback

Two assemblers produce the identical runtime files map:

- The catalog loader: `catalog.ts` statically imports each bundle file
  as text (`import x from "../../catalog/<id>/index.html" with
  { type: "text" }`) and assembles the files map at module load, so the
  bundled Worker carries the files exactly as it carries the definitions
  today.
- The repo-tooling assembler: `build-catalog-index.ts` and the catalog
  harness read the on-disk files, assemble, validate, and fingerprint.

Verification task (phase 1) proves the Kody bundler inlines text
imports, using a probe import in the mock/dev environment. Fallback, if
it does not: the generator emits an assembly module (a generated file
mapping id to files, imported by `catalog.ts`). The generated file is a
build artifact, not the authoring source — the on-disk files stay the
single source of truth. Do not assert text imports work until the probe
passes.

Probe result (Nov 7, 2026): FAIL. A probe module
`scripts/probe-text-import.ts` importing `../probe-text-fixture.html`
with `{ type: "text" }`, run via `kody execute --target mock`, was
rejected at bundle time: `Importing with a type attribute of "text" is
not supported`. Probe files removed after the run. Approach decided:
the generator-emitted assembly module fallback. `catalog.ts` does NOT
use text imports; `scripts/build-catalog-index.ts` emits the assembly
module and `catalog.ts` imports it.

### Decision 5 — DEVIATION: install stays static-import; there is no fetch

This deviates from the brief, which said "install fetches the
definition plus the bundle files, with a hash check against the index
fingerprint before writing". That does not describe the current code:
`install_from_catalog` and `update_from_catalog` use the statically
imported definition; there is no fetch path for catalog definitions;
the canonical "Shipped catalog" requirement says the definitions are
statically imported for install. The on-demand fetch model from the
catalog-restructure spec was never implemented.

Consequences, recorded here so the deviation is explicit:

- There is no partial-fetch case at install, because nothing is fetched
  at runtime. Atomicity moves to generation time: the generator fails
  the build on a missing or unresolvable bundle file, so a broken app
  never ships; and to the existing single-write `add_app` path, which
  writes the assembled definition as one unit, exactly as today.
- The index records `bundleFiles` for verification (the harness and the
  generator check the on-disk files against the assembled definition),
  not for fetching.
- The on-demand fetch model stays unimplemented and is not part of this
  change. If it is ever built, it reopens the partial-fetch question
  (and the allowed-host question recorded in catalog-restructure).

Flagged for the parent's review: the spec is written against the real
mechanism, not the brief's fetch premise.

### Decision 6 — Reference contract and validation

The supported reference forms are exactly `<script src="path"></script>`
and `<link rel="stylesheet" href="path">`, matching the existing
inliner regexes in `client.ts`.

- A reference MUST be a bare relative bundle path exactly matching a
  manifest key. `bundleFile` does an exact key lookup, so a `./` prefix
  (`./store.js`) does not resolve — validation rejects it.
- A reference that does not resolve to a manifest file is an error at
  validation (install/update) time. The render-time drop stays as a
  fail-closed fallback for already-stored definitions.
- An unreferenced `.js` / `.css` file in the manifest is an error (dead
  file). This changes current behavior: `renderBundleContent` today
  appends unreferenced `.js`/`.css` files as inline blocks. That append
  is exactly the loader magic Decision 1 rejects — code executing that
  the author never referenced — so the append fallback is REMOVED.
  No catalog app is affected (only the App Store has extra files and it
  references both). Already-installed custom apps with unreferenced
  files stop executing those files (fail-closed, the safe direction)
  and fail validation on their next update until fixed.
- An unreferenced `.html` file other than the entry stays ignored
  (current behavior). It is never served, so it is inert rather than
  dead code that executes.
- Attributes beyond `src` / `href` (and `rel` for link) on a reference
  element are rejected by validation: the inliner drops attributes
  silently today, so an `async` or `type="module"` script would
  silently lose its meaning.
- Absolute and external URLs in `src` / `href` are rejected by
  validation (the self-containment rule: no external resources).

The ES2019 ceiling applies to on-disk `.js` files exactly as it applies
to inline bundle scripts today, checked by the same grep. The 256 KiB
total cap is computed from the on-disk files' byte lengths.

### Decision 7 — Fingerprint and versions are unchanged by the move

The fingerprint logic is unchanged: it hashes the assembled canonical
form, so a content-identical extraction fingerprints identically.

Migration needs no `catalogVersion` bump for any app. The assembled
canonical definition is byte-identical to the pre-migration one, so no
installed app changes status — parallel to the `installMode` carve-out
already recorded in the "Catalog version" requirement. (Strictly, the
`definition.json` file changes; the rule is about content as experienced
by installed apps, and the content is unchanged.)

No `DEFINITION_SCHEMA_VERSION` bump (currently 5): the inline form
stays valid, so this is not a breaking definition change. The type
comment in `types.ts` requires a bump only on a breaking change shipped
with a migration; none is needed here.

Package version: MINOR expected, decided at the implementation commit
(per the repo pattern).

### Decision 8 — Migration is mechanical extraction, verified by fingerprint

A script extracts each of the 18 catalog apps: for each bundle file in
the inline map, write the content to a real file (byte-identical); then
rewrite `definition.json`'s bundle to the manifest form. Verification
is fingerprint equality: the assembled post-migration fingerprint MUST
equal the pre-migration fingerprint for every app (that equality is the
proof the content is unchanged, and the justification for no version
bump). `RECIPE.md` files are untouched. Inline `<style>` / `<script>`
blocks inside an extracted `index.html` stay inline during migration;
splitting a block into a referenced file is a separate, later edit.

## Open questions

- OQ1: Does the Kody bundler inline text imports? DECIDED Nov 7, 2026
  by the phase 1 probe (Decision 4): NO (`with { type: "text" }` is not
  supported). The generator-emitted assembly module is the approach.
- OQ2: Sequencing with help-about-built-in's in-flight sync. The
  concurrent agent is archiving shell-settings, then help-about-built-in,
  whose deltas touch app-registry ("Catalog index", "Catalog version").
  Whoever archives second reconciles the two deltas' texts against the
  then-current canonical spec. This change's deltas were written against
  the canonical text as read Nov 6, 2026.
- OQ3: The canonical "Catalog index" requirement still carries stale
  collections text and the "Index lists collection recipes" scenario
  (collections were removed; the harness already asserts no collections
  section). This change's MODIFIED delta carries them verbatim so the
  validator accepts it; a canonical cleanup is owed separately, not
  here.

## Risks

- The bundler may not support text imports (Decision 4 fallback exists).
- Removing the append fallback changes rendering for already-installed
  custom apps with unreferenced files (fail-closed; noted in Decision 6).
- The concurrent sync (OQ2) may change the canonical app-registry text
  this change's deltas were written against; the phase 6 reconciliation
  task covers it.
