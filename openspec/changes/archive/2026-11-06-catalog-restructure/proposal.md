# Proposal

## Why

Today the catalog is 20 flat `*.bundle.json` files in `pkg/catalog/`,
imported one by one into `pkg/src/apps/catalog.ts`. Each app is a single
file: there is nowhere to put the install procedure an agent needs beyond
the JSON itself, and there is no machine-readable index of what the
catalog holds — the Store re-derives its listing from the imported
definitions every time. That blocks the recipes direction (Nov 6, 2026):
every app is two parts, a `RECIPE.md` and a JSON file, with the App Store
as the first app with a non-trivial recipe; and it blocks the catalog work
that
follows (`catalog-out-of-pkg` moves the catalog out of `pkg/`;
`public-pinned-catalog` publishes it). Both later changes need per-app
directories and an index to point at. Doing the restructure now, while the
catalog is still in `pkg/` and still statically imported, keeps the move
small and verifiable: same definitions, same fingerprints, no installed
app changes status.

Installing the App Store today is also a single-app step
(`install_from_catalog('app-store')`), but a fresh shell with only the
Store installed is barely usable — the empty-state help that points at
the Store assumes Help and About are there to explain the shell. The
recipe model fixes that at the source: a recipe is a procedure of steps,
an install step names one app, and one recipe may install several apps —
so the App Store recipe installs the Store plus Help and About, and the
empty-state prompt says the same thing.

## What Changes

- Each catalog app moves from `pkg/catalog/<id>.bundle.json` to its own
  directory, `pkg/catalog/<id>/definition.json`, moved unchanged (same
  content, new path/name). No definition content changes except the
  `installMode` field below, and no `catalogVersion` is bumped for the move.
- Each app directory gains a `RECIPE.md`: the install recipe for that app.
  Default is the trivial recipe — install the sibling `definition.json`
  via `install_from_catalog('<id>')`, verify with `list_apps`. A
  non-trivial recipe only where the app genuinely needs setup beyond install.
- `installMode` is declared in the definition, and only where it is
  needed: the default is unattended install from JSON, and most
  definitions get NO new property at all. Only apps with a non-trivial
  recipe carry an `installMode`: `"recipe-or-json"` (recipe for full
  configuration; JSON install also works) or `"recipe-only"` (must be
  installed via the recipe; no current members). Today that is three
  apps, all `recipe-or-json`: `app-store`, `daily-feed`, `generic-feed`
  (see design.md for why each one, and why the other candidates were
  refuted).
- A recipe is a procedure made of steps; each install step names one app,
  so one recipe may install any number of apps. An app's own recipe
  covers that app alone: the App Store recipe installs the Store alone
  and verifies it with `list_apps`. A collection recipe is a standalone
  recipe that installs a set of apps together: the proposed starter
  collection installs `app-store`, `help`, and `about` (one
  `install_from_catalog` step per app), then verifies all three with
  `list_apps`. Help and About themselves stay unattended JSON installs
  with no new property. The empty-state "Install the App Store" prompt
  points at the collection recipe: same three apps, same verify step
  (see shell spec delta).
- A generated index, `pkg/catalog/catalog.json`, lists every catalog app:
  id, label, catalogVersion, fingerprint, installMode, definitionPath,
  recipePath. It is generated by `scripts/build-catalog-index.ts` (repo
  tooling, outside `pkg/`), never hand-written; editing an app requires
  re-running the generator, and the catalog harness enforces that the
  index matches the directories and the definitions.
- `pkg/src/apps/catalog.ts` repoints its 20 imports to the new locations
  and uses the index for the listing summaries; definitions stay
  statically imported for `get_catalog_definition`/install, and the
  explicit import list is retained (the Worker has no directory listing
  at runtime).
- `tests/catalog-harness.ts` walks the app directories and checks index
  == directories == definitions (ids, alphabetical order, catalogVersions,
  fingerprints, install modes), and that every definition still validates,
  installs in a blank store, and holds its initial state. Unknown id still
  returns null.
- `pkg/catalog/README.md` documents the new layout, the generator rule,
  and the recipe/install-mode rules. Stale `*.bundle.json` path references
  elsewhere (test files, docs, code comments) are updated.

## Capabilities

### New Capabilities

- `catalog-restructure`: the catalog is a set of per-app directories
  (`definition.json` + `RECIPE.md`) with a generated `catalog.json`
  index; recipes are the install procedures; apps with a non-trivial
  recipe declare `installMode: "recipe-or-json"` or `"recipe-only"` (no
  current `recipe-only` members); collection recipes install sets of apps.

### Modified Capabilities

- `app-registry`: the shipped-catalog requirement names per-app
  directories and the generated index; a new recipe-install-mode rule
  governs the `installMode` declaration; the catalog-version bump rule
  gains a carve-out for adding `installMode`.
- `authoring`: the catalog-layout requirement names per-app directories,
  `definition.json` + `RECIPE.md`, and the generator rule.
- `shell`: the empty-state App Store prompt installs the App Store plus
  Help and About, matching the App Store recipe.

## Impact

- `pkg/catalog/` (20 moves + 20 `RECIPE.md` files + generated
  `catalog.json` + README), `pkg/src/apps/catalog.ts` (import paths,
  index-driven summaries), `pkg/src/apps/types.ts` +
  `pkg/src/apps/registry.ts` (`installMode` type, validation, canonical
  preservation, fingerprint exclusion), `scripts/build-catalog-index.ts`
  (new), `tests/catalog-harness.ts`, 13 `pkg/catalog/tests/*.cjs` files +
  3 root test files (path references), `pkg/docs/setup.md`,
  `pkg/src/apps/INTEGRATION.md`, comments in `pkg/src/apps/index.ts` and
  `pkg/src/index.ts`, the empty-state prompt in `pkg/src/apps/client.ts` +
  the Help bundle + the README quote (three-app install).
- No storage-schema change, no MCP export change, no change to
  `add_app`/`remove_app`/`list_apps` behaviour. No installed app changes
  update status: `installMode` is excluded from the definition fingerprint
  exactly like `catalogVersion`, so fingerprints — and therefore install
  snapshots and update statuses — are byte-identical for every installed
  app. No `catalogVersion` is bumped for the move or for adding
  `installMode` (see design.md).
- This change does NOT move the catalog out of `pkg/`, does NOT make
  anything public, does NOT change the Store UI to display recipe prompts
  (the data lands now; the Store display is a follow-up that reads
  `installMode` from the index), does NOT add
  per-app READMEs, and does NOT introduce fetch-on-demand install
  (definitions stay statically imported; the index is the seam for later,
  not a fetch mechanism now).
- Relation to `catalog-out-of-pkg` (pending): that change moves the
  catalog to the repo root and adds its own `catalog/index.json` manifest.
  This change is its in-`pkg/` precursor: the per-app directories and the
  generated index land first, so the out-of-`pkg/` move later moves
  directories instead of flat files. That change's manifest field list
  (id, name, label, icon, category, description, catalogVersion, bundle
  path, fingerprint) predates `installMode`, `recipePath`, and the
  `collections` section and will need
  reconciling when it is implemented — flagged in design.md, not fixed here.
- Version: the implementation commit records the decision; MINOR is
  recommended (new index + recipe files, no behaviour change for installed
  apps). Build increments by 1 on publish either way, per `pkg/AGENTS.md`.
