# Design: manifest-driven-store-rows

## Context

The Nov 6 catalog-restructure change specified that listing
summaries SHALL be driven by the generated index, with
definitions fetched only for install. The remote-catalog move
(Nov 8, catalog out of `pkg/`) kept the manifest shape but
never enriched it, and the version gates added since
(`minPackageVersion`, schema floor, capabilities disclosure)
were implemented as definition fetches instead of manifest
fields. The result, verified Nov 12, 2026 against `main` at
`24f6c3a`: a Store open costs 1 listing-manifest fetch, 19
definition fetches in `list_catalog`, 19 more in
`buildStoreRows`, and 1 manifest + 1 definition fetch for
the Store self-update check — ~40 outbound fetches against
Kody Free's 1,000/day. The manifest is the listing; the fix
is to make it carry what the listing displays.

## Decisions

### 1. Manifest entries carry the display fields

Each entry gains, copied from the definition by the
generator (which already reads every definition at build
time):

- `name`, `icon`, `category`, `description`,
  `schemaVersion` — required. Every catalog definition
  today carries all five.
- `minPackageVersion` — optional, omitted when the
  definition carries none (today only `app-store` has
  one, `4.2.0`).
- `capabilities` — required, in exactly the
  `summarizeCapabilities` shape: `manageApps` (boolean),
  `feedHosts` and `proxyHosts` (sorted host arrays),
  `themeView` and `themeSet` (booleans). Computed by the
  generator with the existing `summarizeCapabilities`,
  so the manifest carries hosts, never full upstream
  URLs. A definition with no capabilities yields the
  all-false / empty summary, never an absent field.

The fingerprint is unchanged: it hashes the assembled
definition, not the manifest, so enriching the manifest
changes no fingerprint and no installed app's status.
No definition file changes, so no `catalogVersion` bumps
and no Store definition change.

### 2. Listing reads the manifest only

`list_catalog` builds each `CatalogSummary` from its
manifest entry — same fields plus the additive
`capabilities` field, new source — with no
`fetchDefinitionJson` call.
`buildStoreRows` drops the per-row
`get_catalog_definition_meta` call and reads
`minPackageVersion`, `schemaVersion`, and `capabilities`
from the summary it already receives. The installed
definition still wins for label / name / icon / category
/ description when the app is installed (unchanged
precedence); the summary is the source for uninstalled
apps and for the gates. `getStoreSelfUpdate` reads the
App Store entry from the discovery manifest
(`catalogVersion` and `minPackageVersion` both live
there now) instead of fetching its definition.

`get_catalog_definition_meta` stays as a public export:
agents and `get_catalog_definition` still use it, and it
still fetches one definition. Only the Store rows and
self-update paths stop calling it. `get_catalog_definition`
(install / update / restore / absorb) is unchanged: it
still fetches the definition and its bundle files.

### 3. The manifest summary is display-only

The update-confirmation gate (`capabilityAdditions`)
still compares full definitions fetched by
`get_catalog_definition`. The manifest `capabilities`
summary never feeds that gate, so a stale or
hand-edited manifest cannot smuggle a capability past
confirmation — the worst it can do is mislabel a row,
and the harness (decision 5) prevents shipping a
mismatched manifest. Status classification
(`get_app_status`) is already manifest-only via
`get_catalog_entry` and does not change.

### 4. Compatibility: old shells ignore the new fields

`validateManifestEntry` picks known fields into the
returned entry and ignores unknown ones (verified in
`pkg/src/apps/remote-catalog.ts`). An old shell reading
an enriched manifest therefore lists exactly as before
and keeps fetching definitions — wasteful, but working.
No line advance, no tag freeze, no Store update is
needed to ship the enriched manifest. Deploy order is
manifest first (regenerate, push, move tag `4.2` — a
release act needing its own direction), shell second.

The reverse is not free, and is recorded honestly: a
new shell REQUIRES the new fields, so a manifest
missing them fails validation exactly like one missing
`bundleFiles` today, and the Store falls back to
installed apps plus a catalog error. Any catalog base
— including a third-party one — must be generated by
the current generator. That is the same bar the index
already sets for `bundleFiles`, not a new kind of
requirement.

### 5. Generator and harness enforce the shape

`scripts/build-catalog-index.ts` copies the fields and
`tests/catalog-harness.ts` checks them against the
definitions (name, icon, category, description,
schemaVersion, minPackageVersion presence/value,
capabilities summary via `summarizeCapabilities`), the
same way it already checks label, catalogVersion,
fingerprint, installMode, paths, and bundleFiles.
Regenerating from unchanged definitions stays
byte-identical. `catalog/README.md` line 56 enumerates
the entry fields and is updated in the same change.

### 6. Fetch budget after this change

A Store open costs 2 outbound fetches: the listing
manifest (tag base) and the discovery manifest (main
base, self-update check). The 30-second in-memory
manifest cache is unchanged, so rapid re-opens within
the window reuse both. Feeds are untouched. The
enriched manifest measures 17.7 KB for the current 19
apps, well under the 64 KiB cap, so no cap change.

### 7. Version: PATCH

Shell 4.2.1 → 4.2.2, build 48 → 49. This restores
documented behavior (listing summaries driven by the
index) with no observable row change, no MCP shape
change besides the additive `capabilities` field on
`list_catalog` summaries, and no new feature — PATCH
under `pkg/AGENTS.md`. The reverted 4.3.0/49 pair stays
unused; the new pair 4.2.2/49 has never existed, so
nothing is reused. `pkg/package.json` plus the
`pkg/AGENTS.md` and `pkg/README.md` headers move in the
same commit as the change. No catalog app's
`catalogVersion` moves.

## Failure modes

- **Manifest missing a new field.** Validation fails
  the whole manifest; the Store shows installed apps
  with the existing honest catalog error and retry.
  The harness prevents shipping this from this repo.
- **Stale manifest (tag moved, edge cache lags).**
  Unchanged from today: rows render from the stale
  listing until the cache catches up; definitions are
  not consulted, so a stale row cannot be "corrected"
  by a fresh definition fetch the way it silently was
  before. The row's `catalogVersion` still comes from
  the manifest, so staleness is visible the same way
  it is today.
- **A definition changes without regenerating.**
  The harness fails, as today. The generator is the
  single writer; the manifest is never hand-edited.

## Open questions

None. The one judgment call — PATCH rather than MINOR
— is decision 7 with its reasoning; the reviewer may
overrule it to MINOR (4.3.0, build 49) before
implementation.
