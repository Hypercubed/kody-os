- [ ] 1.2 Ceiling-scan the BUILT file and fail the build loudly on any of: `?.`, `??`, logical assignment (`||=`, `&&=`, `??=`), or calls to `replaceAll`, `structuredClone`, `Object.hasOwn`, `.at()`, `WeakRef`, `FinalizationRegistry`, `URLPattern`. (The scan matches CALLS, not mentions — the probe's own table labels and `typeof` checks name the built-ins.) Record the result. The `adoptedStyleSheets` write inside Lit's `adoptStyles` is recorded as `builtin-ok` (dead code for light-DOM use: both probe elements override `createRenderRoot()`; the API is native since Chrome 73), never a fail. The entry SHALL NOT import `ContextRoot` (the only `WeakRef` in `@lit/context`); prove it is not in the bundle with per-output `bytesInOutput: 0`, not the metafile-inputs list (which includes tree-shaken modules)
- [ ] 1.3 Decide the provision mechanism (design Open Question 1: asset under `pkg/public/` served via `/_assets/`, or inlined into the shell client) and the global name (design Open Question 4), and expose the vendored Lit under one documented global in the pattern of `window.KodyBridge`, loaded once per page in every placement where app sections render (page, widget, modal). ## 3. Islands — the architecture

- [ ] 3.1 Pin the island contract in the shell spec and the authoring docs: a section is an island; the server renders the JSON state seed + skeleton HTML (the no-JS content) before bundle scripts run; the island's bundle mounts onto it (a LitElement or a lit-html `render()` call) and adopts its starting state from the JSON seed; one bridge store instance per section; failure contained to its section with native form submission as the fallback; islands load at `DOMContentLoaded`
- [ ] 3.2 Port the Counter bundle to the provided Lit + adapter without behavior change; the harness scenarios and `kody dev` E2E checks must pass identically, and the ported bundle must be byte-checked against the same state/action behavior as the hand-rolled reference
- [ ] 3.3 Port a second stateful app to the provided Lit + adapter without behavior change; if the port needs adapter or shared-element changes, revise and re-verify the Counter port. Only after the second port is green is the provided surface declared the recommended path for stateful apps in the docs; if no second consumer is found, record that outcome and keep the provision marked provisional (do not declare it recommended on one app's evidence)

## 4. Bridge-only state — the rule

- [ ] 4.1 State the rule in the shell spec and the authoring docs: a component written under this change reads state ONLY from the bridge store (a `KodyBridge.create(section)` subscription, or context derived from it). The JSON seed is the initial handoff, read once at mount. A component SHALL NOT read state from server-injected DOM — no span scraping, no `data-value` attributes, no reading server-rendered text as state. The `[data-field]` spans stay in the served HTML as the no-JS content and the fallback; existing span-reading bundles keep working until ported (dual-channel migration)
- [ ] 4.2 Add the rule to the pre-`add_app` authoring checklist ("stateful bundle uses the provided surface, or records why not" gains "and its components read state only from the bridge store"), and evaluate a harness/static check for it (a component reading `[data-field]` spans or `data-value` attributes fails the check); ship the check only if it catches a class of defect review cannot, and record the evaluation either way
