# Proposal

## Why

The Counter Reset saga (2026-10-27/28) shows that authoring a correct app from the current docs is hard even for a careful agent with the code in front of it. Three defects survived two rounds of "fix it" before the bundle behaved, and each came from a contract the docs state incompletely or not at all:

1. **The bundle reads its initial state from the wrong place.** The bundle assumed a `[data-value]` attribute on the state readout. The renderer (`pkg/src/apps/client.ts`, `renderAppSection`) emits a plain `<span>` inside `<p data-field="...">` — no `data-value` anywhere — so the bundle silently fell back to a hardcoded `0`. The guide says the renderer adds `data-field` hooks "automatically" and that "app authors do nothing special." That is false for any bundle that displays state.
2. **Shell-owned forms race bundle-owned fetches.** Reset is a shell-rendered `ui.actions` GET form. The shell client replays it with `?format=json` and patches only the `[data-field]` span, never the bundle's display or internal counts. The fix needed a capture-phase submit claim scoped to the app's own form, an optimistic paint, a single-flight ordered queue shared with the step buttons, and a sequencing guard so a late shell patch cannot discard a newer step — plus a `MutationObserver` fallback for the path where capture does not deliver. None of that interaction is documented; the guide's Scribe section says only "the shell may replay the same GET action ... and patch fields in place."
3. **Docs drift from the code.** The guide's troubleshooting section still says "Re-adding reset the state," which has been false since the action-schema-v2 migration made re-adds preserve state by default. `pkg/AGENTS.md` still says the package is v0.1.5 and that `ui.template` is "frozen ... required by the validator," which has been false since schemaVersion 4 removed the field. An agent following the published docs designs against a shell that no longer exists.

The underlying lesson is structural, not personal: the bundle/shell boundary is a real protocol (rendered markup, patch scope, form ownership, fetch fallback, ES2019 ceiling), and today it lives mostly in code and in one agent's working notes. Better docs are the minimum; a small shared implementation of the protocol once — provided by the shell, so the next app uses it instead of re-deriving it — is the durable fix. This change specs both, in phases, with the docs as the binding contract and the shell-provided framework as the recommended path for stateful bundles. The deeper diagnosis, recorded 2026-10-28: every stateful app author currently invents their own reactive system. The aim of Phase 2 is therefore a framework the shell itself provides — loaded once, free to every app, the JS analogue of the shell-provided shared CSS — which all apps with state should use. Not every app needs it, but no stateful app should have to re-derive reactivity. Isolation between apps sharing one page and one framework is the interesting problem Phase 2 must solve first.

Note on premise (2026-10-28): the early assumption that the Scribe had very bad JavaScript support — which motivated HTML-first, no-JS-tolerant rendering — is retired; JavaScript is assumed. This change documents the resulting span-based state contract as current behavior only. Replacing it with a structured state handoff is a future change, not part of this one.

## What Changes

**Phase 1 — Docs (binding).** Rewrite the bundle-authoring contract in `pkg/docs/adding-an-app.md` (and fix `pkg/AGENTS.md` in the same pass) to state the full protocol: exact rendered markup, shell-client patch semantics, form ownership and the capture/sequencing pattern, initial-state reading, `data-action-base` resolution, the ES2019 ceiling pinned in one place, and a pre-`add_app` authoring checklist. Correct the known drift (re-add state preservation, template removal, version header, pin-vs-home wording). Align the local-preview docs with the canonical `kody dev` path: commit `b301418` (2026-10-28) removed `dev/` and added the `kody dev` instructions plus `pkg/scripts/registry.ts` and `pkg/scripts/seed-dev-hash.ts`, so `adding-an-app.md`'s create-once script instructions and the stale `dev/preview.mjs` references in `pkg/examples/README.md` and the counter harness header must be updated to that reality.

**Phase 2 — Shell-provided framework (select, provide, port).** Evaluate the candidates — Svelte (plain compiler only, not SvelteKit), Custom Elements / Web Components (vanilla platform; Lit not evaluated first), the microframeworks re:dom and VanJS, and Alpine.js (directive-based, no build step) — on provision feasibility and isolation first (per-section instances, no shared mutable state, no global-scope or registry collisions, no style leakage, failure contained to its section), then on the existing gates (size, ceiling compliance, harness scenarios against real shell markup, Scribe-engine probe). Select one framework for the shell to provide, implement its provision (mechanism per design Open Question 2) together with the shell-bridge adapter instantiated per app section, and port the Counter bundle to it as the first consumer, then a second stateful app. Phase 1 docs name the provided framework as the recommended path for stateful bundles but cannot document its concrete surface until selection; Phase 2 updates the docs with the surface, version, and fallback rules. A framework does not replace the adapter; per-app vendoring/compilation remains a documented fallback, not the recommended path.

**Phase 3 — Verification tooling (should).** Generalize the Counter verification pattern — a jsdom harness driving the real bundle plus a simulated shell-client patch with controlled fetch timing, plus `kody dev` end-to-end checks (real shell rendering via `kody dev fetch`/curl against the mock server) — into documented, reusable form. Evaluate (do not assume) a static bundle lint (`validate_bundle`) covering the ES2019 ceiling and the contract's checkable rules.

- Explicit non-goals: no new effect operators, no declarative UI, no `act()`/registry semantics changes, no framework mandate for every app (stateful bundles SHOULD use the shell-provided framework; stateless bundles may stay plain; no forced migration of existing apps), no bundle-cap or storage-budget changes, no changes to the shell client itself beyond what the docs pin (the client is the reference behavior; the provided adapter adapts to it).

## Capabilities

### New Capabilities

- `authoring`: the bundle/shell interaction contract becomes a documented, scenario-pinned part of the authoring spec, with a reference implementation and a pre-`add_app` checklist. (The shell-provided framework and adapter surface is a new `shell` capability, not a new runtime capability for bundles.)

### Modified Capabilities

- `authoring`: guide accuracy requirements gain drift-correction scenarios (re-add preservation, template removal, version header).
- `shell`: the rendering contract (state markup, action forms, client patch scope and fallback) gains scenario-pinned requirements, so future shell changes cannot silently break conforming bundles; the shell additionally provides the framework and adapter surface (loaded once per page, versioned, per-section instances, isolation guarantees) as a scenario-pinned capability.

## Impact

- Docs only in Phase 1: `pkg/docs/adding-an-app.md`, `pkg/docs/scribe-limitations.md` (ceiling cross-reference), `pkg/AGENTS.md`, `pkg/examples/README.md` (checklist + harness pointers). No code, no publish strictly required for docs to help — but the docs ship in the package, so they reach agents on the next publish.
- Phase 2 code: shell provision of the selected framework and the per-section adapter (asset/client code under `pkg/src/` + `pkg/public/` as the mechanism requires); a publish is required before any app can use the provided surface. The selection evaluation produces a decision record (evidence + selection) first; no provision ships without passing the isolation gates.
- BREAKING: none. Additive docs and an additive shell-provided surface; existing bundles keep working unchanged, and no app is forced to migrate.
