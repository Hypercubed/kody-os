# Design: agent-app-authoring

## Context

See proposal.md (Why). The evidence, all verified against the code on 2026-10-28:

- **Rendered markup** (`pkg/src/apps/client.ts`, `renderAppSection`, lines 125–168): bundle HTML, then one `<p data-field="<name>"[ hidden]>` per state field containing `<span><value></span>` (plain span, escaped value, no `data-value` attribute), then one `<form class="app-action" method="GET" action="<base>/apps/<id>">` per `ui.actions` entry with hidden `action` (+ `k`/`from` when present) inputs and a submit button. `hideState: true` adds `hidden` to the `<p>`; the span stays in the DOM.
- **Client patch semantics** (`pkg/src/client/index.ts`): on submit, the client replays the form URL with `?format=json`, and on `{ ok: true, state }` patches only the `[data-field]` spans inside the nearest `[data-app-id]` scope (or document), setting each span's `textContent` from the returned state. Any failure falls back to native `form.submit()`. It never touches bundle-owned DOM or bundle variables.
- **Form funnel** (`pkg/src/apps/forms.ts`, `actFromForm`): shell form submissions become `act()` calls with string args; `format` is stripped before `actFromForm`. UI and MCP share the one `act()` handler.
- **Ceiling**: `pkg/docs/scribe-limitations.md` binds "vanilla ES2019" with an on-device Chromium 80 probe; `pkg/AGENTS.md` additionally notes `?.`/`??` crash Chromium 75. The Counter work additionally avoided arrow functions, `const`/`let`, `async`/`await`, and template literals in bundle code, and waited for `DOMContentLoaded`. The exact binding list is currently split across two docs with different engine versions named — a defect this change fixes by canonicalizing it (see Open Question 1).
- **Retired premise (recorded 2026-10-28, user correction):** the early design assumed the Scribe had very bad JavaScript support, which motivated HTML-first / no-JS-tolerant rendering (state painted into the page as text, forms that work by native submit). On-device probe evidence (Chromium 80 engine; fetch/XHR, timers, localStorage, ES2019 proven, `pkg/docs/scribe-limitations.md`) and live apps verified on the Scribe retire that premise: JavaScript is assumed. The span contract pinned in this change therefore documents current behavior only — it is not justified by no-JS support, and replacing it (e.g. a structured JSON state handoff to bundle code) is a future change, explicitly out of scope here.
- **Verification that caught the bugs**: a jsdom harness running the real bundle with a simulated shell-client patch and manually-resolved fetch promises (so clicks land mid-flight), covering Reset latency, Reset-then-step ordering, and stale-response flashes; plus end-to-end checks against real shell rendering. The repo harness (`pkg/examples/tests/counter-tests.cjs`) simulates the client patch — it talks to no server and no Kody. An earlier scratch harness drove the real served client via the repo preview server (`dev/preview.mjs`); that server was removed in commit `b301418` (2026-10-28), and the live-rendering leg is now `kody dev` (mock server + `kody dev fetch`/curl, see `pkg/README.md` and `pkg/AGENTS.md` "Local dev"). Neither is documented as the authoring verification path today.
- **Compiled-framework background (Svelte, raised 2026-10-26 and again 2026-10-28; not yet evaluated):** Svelte was discussed on Oct 26 alongside Custom Elements/Lit as bundle-authoring replacements — not data-schema replacements — with no adoption decision then. Search-derived claims to be verified by the evaluation, not asserted here: Svelte is a compiler emitting vanilla JS with no virtual DOM or shipped runtime; Svelte 5 uses Proxies for runes reactivity and requires a modern browser, its components are always hydratable with `mount()`/`hydrate()` entry points, and its default output targets modern JS (ES2020 per a secondary source). None of this has been probed on the Scribe engine, and no Svelte output has been run against the shell contract.
- **Web Components background (Custom Elements, raised 2026-10-26, revisited 2026-10-28; not yet evaluated):** platform-native, no build step and no shipped dependency — a bundle defines elements with `customElements.define()` in its own JS. Compatibility data says Custom Elements v1 shipped in Chrome 54 and Shadow DOM v1 in Chrome 53, both below the Scribe's Chromium 80 engine, but that is not Scribe evidence: the stripped-down, JIT-less Scribe browser still needs a probe. Bundle inlining order matters for timing: `renderBundleContent` appends extra `.js` files as `<script>` tags after the inlined `index.html`, inside the `.bundle` div — so a custom-element tag in `index.html` is parsed before its defining script runs, and upgrade-on-define (spec behavior) is the path, with the paint/upgrade timing on e-ink untested. Shadow DOM isolates styles: the shell's shared `os-*` classes do not pierce a shadow root, so shadow-DOM vs light-DOM authoring is an open evaluation question, not a default.
- **Microframework background (re:dom and VanJS, raised 2026-10-28; not yet evaluated):** search-derived claims to be verified by the evaluation, not asserted here. re:dom is a ~2 KB library of direct-DOM helpers (`el`, `mount`, keyed `list`), no virtual DOM, no template language; components are objects with an `.el` and an explicit `update()` — updates are manual, not reactive. VanJS is a ~1.0 KB gzipped reactive framework with five functions (`tags`, `add`, `state`, `derive`, `hydrate`), no transpilation or build step, whose state reactivity uses getters/setters on a `val` property (not Proxy, per its source analysis) and which ships a `nomodule` build. Both are single-file distributions. Under the shell-provided direction below, the question for both changes: instead of vendoring a copy into each bundle, the shell loads the library once and every app uses it — so the evaluation judges provision + isolation, not per-app vendoring.
- **Alpine.js background (raised 2026-10-28; not yet evaluated):** search-derived claims to be verified by the evaluation, not asserted here. Alpine v3 is a directive-based framework for server-rendered HTML: behavior is written as `x-*` attributes on the shell-rendered markup (`x-data` scopes, `x-text`/`x-show`/`@click` and friends), no build step, single script tag, mounts by scanning the document for `x-data` and keeps a MutationObserver running for later-injected HTML. Reactivity is Vue 3's `@vue/reactivity` (Proxy-based). Attribute expressions are compiled with `new Function`. Size claims conflict across sources (7 KB to ~17 KB gzipped depending on build) — the evaluation must measure the actual build it would ship. `x-data` scopes are isolated per element, but `Alpine.data()` and `Alpine.store()` are global registries (stores must be registered in an `alpine:init` listener before `Alpine.start()`; late registration makes already-rendered components evaluate `$store.<name>` as undefined and log expression errors) — so namespacing and registration timing are isolation questions, not defaults.
- **Watch list — A2UI (raised in the 2026-10-27 standards survey; reaffirmed 2026-10-29, user direction: keep an eye on it; NOT a Phase 2 candidate).** A2UI (Agent-to-User Interface) is Google's open, JSON-based streaming protocol for agents to describe UIs declaratively: the agent sends component definitions plus a data model (`createSurface` / `updateComponents` / `updateDataModel` / `deleteSurface`), and the host renders them from its own catalog of trusted components — the agent describes, the application decides how it renders. Status checked 2026-10-29: v0.9 stable family, v0.9.1 current production release, v1.0 still a candidate, v0.8 legacy; described as an early-stage public preview and a living document, not an ISO/IETF standard. It is watched because it is the standards-track answer to the declarative direction this change keeps out of scope (declarative UI may return; the user prefers composing existing standards), and because it maps onto the data-model-first direction: a future where an agent emits UI descriptions instead of executable bundle code. No evaluation task in this change. Revisit when: v1.0 stabilizes, a web renderer exists that runs under the ES2019/Scribe ceiling, or Kody or the surrounding agent ecosystem adopts it. The Phase 2 selection record notes the current A2UI status at selection time, so the decision is made with the watch item current.
- **Shell-provided direction (2026-10-28, user direction):** pick one small framework for the shell itself, so it is free to use for every app — the JS analogue of the shell-provided shared-CSS end state (Oct 27). Not every app needs to use it, but all apps with state should. The interesting problem is isolation between apps sharing one page and one framework: bundle scripts today are classic `<script>` tags inlined into a single page (`renderBundleContent` appends extra `.js` after the inlined `index.html`, inside the `.bundle` div), so top-level names already share one scope across sections; the Custom Elements registry is global; bundle CSS is page-global. Any shell-provided framework must solve per-section scoping, state, style, registry, and failure isolation — that is the primary evaluation gate, ahead of ergonomics.

## Goals / Non-Goals

- Goals: an agent that has read only the published package docs can author a stateful bundle that (a) initializes from the shell's rendered state, (b) stays in sync with shell-form actions without races, (c) respects the ES2019/Scribe ceiling, and (d) verifies itself before `add_app`, using the shell-provided framework and adapter instead of inventing its own reactive system; the protocol is pinned in specs so shell changes are checked against it.
- Non-goals: mandating a framework for every app (stateless and presentational bundles may stay plain; stateful bundles SHOULD use the provided framework — a recommendation, not a validator mandate, and no forced migration of existing apps); changing `act()` or registry semantics or validator behavior for existing definitions; adding operators; declarative UI (out of scope per the 2026-10-27 direction: the data model matters more than the builder/editor, declarative UI may return later — this change keeps the provided framework and adapter UI-agnostic and data-first).

## Decisions

1. **Docs first, selection second, provision third.** Rationale: docs pin the contract every future author needs with zero runtime risk; the selection evaluation then picks the one framework the shell provides, on isolation evidence; provision ships it in the shell with a per-section adapter, proven by porting Counter first and a second stateful app second. The Counter bundle is the reference implementation in the meantime, annotated to teach. Alternative (provision before selection) rejected: it would enshrine a framework before isolation between apps on one page has been tested.
2. **The shell client is the reference behavior; the provided adapter adapts to it.** Rationale: changing the client to patch bundle DOM would couple the shell to bundle internals it cannot know. The documented pattern (capture claim + observer + queue + sequencing) is the adaptation layer, provided by the shell and instantiated per app section. Alternative (teach the client about bundles) rejected.
3. **Pin the contract in two specs, not one.** Rationale: the authoring spec owns what agents must write; the shell spec owns what the renderer/client guarantee. Splitting them means a shell change that alters markup or patch scope must update the shell spec, and a docs change that promises new behavior must update the authoring spec — neither can drift silently past the other.
4. **Harness-first verification; static lint is an evaluation, not a commitment.** Rationale: the jsdom harness (simulated client patch, controlled fetch timing) caught ordering and staleness bugs no static scan can express (they depend on fetch timing). A static lint for the ES2019 ceiling and checkable rules (e.g. no `window.location.pathname` action URLs) may still help, but only after the harness is documented — otherwise the lint becomes the false assurance the docs were.
5. **No new storage or registry surface for the provided framework.** Rationale: the framework and adapter are shell code/assets, loaded once per page; apps persist state only through `act()` like every bundle. Provision uses the existing asset pipeline (mechanism per Open Question 2); a provided framework that needed new storage keys or registry fields would not be a shell-provided framework at all.
6. **Select one framework for the shell to provide; evaluate provision + isolation first, ergonomics second.** Rationale: every stateful app author currently invents their own reactive system (the Counter bundle's queue/observer/sequencing guard is the worked example). One framework loaded once by the shell is free to every app — zero per-app bytes, one version, no per-app choice to get wrong — and stateful apps should use it. The selection evaluation therefore judges each candidate on whether it can be provided by the shell at all, and whether apps sharing one page stay isolated: per-section instances, no shared mutable state, no global-scope or registry collisions, no style leakage, and failure contained to its section. Per-app vendoring or per-app compilation remains allowed as a documented fallback for apps that need a different version, but it is not the recommended path.

**Svelte (candidate).** Svelte's compiler model fits bundles, but "shell-provided" is awkward for it: components still compile per app, and only runtime helpers could be shared — and its output is ESM in a classic-script bundle world, so the evaluation must determine a provision mechanism (shared runtime bundle, import map, or per-app compile with the shell providing only the adapter) before Svelte can be selected. Tests composition (component + shell-provided adapter), plain compiler only, SvelteKit out of scope. Alternative (adopt Svelte without evaluation) rejected: provision mechanism, engine ceiling, and hydration are all unverified. Alternative (evaluate runtime frameworks first, e.g. React/Vue) rejected: shipping a runtime contradicts the bundle size discipline; if no candidate passes the isolation gates, the fallback is the shell-provided adapter alone, not a runtime framework.

**Custom Elements / Web Components (candidate).** Rationale: native platform, zero build step, zero shipped dependency — "provided" here means the shell supplies naming/isolation conventions and the adapter, since the registry itself is the browser's. It solves encapsulation and lifecycle, not state sync or reactivity: a custom-element bundle still hand-rolls its display updates and still needs the span/`act()` adapter, so the evaluation tests composition (element + adapter). The sharpest isolation question is the global registry: tag names must be namespaced by app id, or two apps collide. Lit is not evaluated first: it is a library layer on top of the platform, and the platform question (upgrade timing, shadow vs light DOM, shared-CSS behavior) must be answered before deciding whether a helper layer is wanted; Lit becomes a follow-up consideration only if the vanilla pattern proves out. Shadow DOM is not assumed: a shadow-root bundle loses the shell's shared `os-*` styles, so the evaluation must test both shadow-DOM and light-DOM variants and record which (if either) is viable.

**Microframeworks — re:dom and VanJS (candidates).** Rationale: the smallest step from hand-rolled bundles — plain JS, no compiler, no platform upgrade questions, library code small enough (claimed ~2 KB and ~1.0 KB) for the shell to load once. They differ from each other in the way that matters: VanJS is reactive (state/derive bindings update the DOM), re:dom is explicit (the author calls `update()` on the changed element) — so the evaluation compares reactive vs manual update ergonomics against the same Counter harness, not just size. Both still need the span/`act()` adapter, and both isolate naturally as pure functions plus per-app state, with nothing framework-owned except the namespace. Scope is capped at these two named frameworks; evaluating the wider microframework field is not part of this change, and a reject on generic grounds (e.g. provision) is recorded once, not re-litigated per library.

**Alpine.js (candidate).** Rationale: the closest fit to the shell's shape — built for server-rendered HTML, no build step, one script load, and `x-data` scopes that isolate per element, which maps directly onto per-section instantiation. Its directives are author-written HTML attributes evaluated as JavaScript, not a JSON declarative UI schema, so evaluating it does not reopen the declarative-UI non-goal. It still needs the span/`act()` adapter (Alpine state must be synced with shell spans and `act()`, e.g. via a per-section store or effect — the evaluation determines the bridge), and its global registries are the isolation risk: `Alpine.data()` and `Alpine.store()` names must be namespaced by app id, stores must be registered before `Alpine.start()` (late registration breaks already-rendered components), and expression compilation via `new Function` must be checked against the ceiling and the JIT-less Scribe engine. If Alpine is selected, the shell owns `Alpine.start()` timing and the registration discipline; apps never call it themselves.

## Risks / Trade-offs

- [Risk] Helper drifts from shell-client semantics after a client change → Mitigation: the harness simulates the client patch semantics, and the shell-spec scenarios pin patch scope; a client change that breaks the simulated semantics must update the harness and the spec together.
- [Risk] Docs drift again (the exact failure this change fixes) → Mitigation: spec scenarios assert the drift-prone statements (re-add preservation, template removal) against behavior, and the apply checklist requires re-reading the cited code lines before publishing the docs.
- [Risk] The ES2019 list is wrong in an edge (engine-version wording differs between docs today) → Mitigation: Open Question 1 is resolved by a probe-first task — state what the on-device probe actually proved, and mark anything beyond it as conservative guidance, not a binding claim.
- [Risk] Over-frameworking: a shell-provided framework becomes a de facto second shell → Mitigation: selection gate (isolation evidence + second-app port) and the SHOULD-not-MUST rule for stateful apps; the provided framework stays an authoring surface, never a registry feature, and existing apps are never force-migrated.
- [Risk] Framework output breaks the ceiling or desyncs from the shell: compiled Svelte output uses modern syntax and owns its subtree, so an unprobed build can fail the ceiling scan or fight the shell client's span patching → Mitigation: the evaluation gates (provision feasibility + isolation + downleveled output + ceiling scan + harness scenarios against real shell markup + Scribe-engine probe) must pass before selection, and the adapter requirement (Decision 6) is part of the evaluation, not an afterthought.
- [Risk] Cross-section leakage: apps sharing one page and one framework instance leak state, styles, or registry names into each other → Mitigation: per-section instantiation is a shell-spec requirement with isolation scenarios (multi-section page, same top-level names, same tag names), and the selection evaluation must demonstrate it before provision ships.
- [Risk] Failure blast radius: an exception in one app's framework/adapter code breaks the shell client or neighboring sections → Mitigation: per-section error containment is a shell-spec requirement; the fallback is native form submission, which must keep working when the provided framework fails.
- [Risk] Version lock-in: the shell picks one framework version for every app, so upgrading it can break existing apps and no app can pin its own → Mitigation: the provided surface is versioned and version changes require spec updates plus re-verification of the reference apps; per-app vendoring/compilation remains a documented fallback for apps that need a different version.
- [Risk] Alpine global registries collide or register too late: two apps registering the same `Alpine.data()`/`Alpine.store()` name overwrite each other, and a store registered after `Alpine.start()` makes rendered components evaluate `$store.<name>` as undefined → Mitigation: namespacing by app id and a shell-owned registration discipline (stores/data registered in `alpine:init`, before start) are selection gates, demonstrated on a multi-section page before provision ships.
- [Risk] Shadow DOM breaks the shared theme: a shadow-root bundle is cut off from the shell's `os-*` classes, so a Web Components evaluation that only tests Shadow DOM could recommend a pattern that silently un-themes apps → Mitigation: the evaluation tests light-DOM and shadow-DOM variants side by side against the shared stylesheet and records the styling outcome per variant.
- [Risk] Fallback version drift: a microframework vendored into a bundle as a fallback is a pinned copy with no update path — every fallback app carries its own, possibly different, version, and a security or ceiling fix must be re-vendored app by app → Mitigation: shell provision replaces per-app vendoring as the recommended path (one version, loaded once); per-app vendoring remains only as a documented fallback with its pinned version recorded, and a fallback app's version drift is its author's responsibility, not the shell's.

## Migration Plan

None forced for existing apps — docs are additive and provision is additive; no bundle, definition, or stored-data changes. Existing bundles (including Counter) keep working; Counter ports to the provided framework first as the reference, a second stateful app ports second, and new stateful apps SHOULD use the provided framework at authoring time. Rollback is a republish of the prior commit, with ported apps reverted to their hand-rolled bundles in the same change.

## Open Questions

1. **Exact ES2019 ceiling list and engine version.** `scribe-limitations.md` (Chromium 80 probe, "ES2019 ceiling") and `pkg/AGENTS.md` ("Chromium 75 crashes" for `?.`/`??`) name different engines, and the Counter bundle additionally avoided arrows, `const`/`let`, `async`/`await`, and template literals. Which list is binding, and what did the on-device probe actually prove? Resolve probe-first in the Phase 1 task; do not assert the stricter list as binding without evidence.
2. **Provision mechanism and per-section scoping.** How is the selected framework provided — package asset under `pkg/public/` served via `/_assets/`, inlined into the shell client, import map, or another route — under what single global namespace, and in which placements (page, widget, modal)? How is app code scoped per section so one section's top-level declarations cannot collide with another's (render-time wrapping, per-section closures, or authoring discipline)? Resolve inside the Phase 2 provision task; the mechanism must satisfy the shell-spec isolation scenarios.
3. **Static lint (`validate_bundle`)**: ship as an MCP export, a repo script, or not at all? Evaluate after the harness is documented; the harness is the requirement, the lint is optional.
4. **Local preview docs — RESOLVED during drafting (2026-10-28, commit `b301418`):** `dev/` was removed and `kody dev` is the canonical path (`pkg/README.md` and `pkg/AGENTS.md` "Local dev" sections, `pkg/scripts/registry.ts` + `pkg/scripts/seed-dev-hash.ts`). The remaining work is alignment, not a choice: `adding-an-app.md`'s create-once script instructions and the stale `dev/preview.mjs` references in `pkg/examples/README.md` and the counter harness header must be updated to that reality (see tasks 1.5). The spec requires exactly one documented verification path.
5. **Svelte branch, downlevel step, and build-pipeline ownership.** Svelte 5 (runes/Proxy, modern output) vs. Svelte 4 (assignment reactivity, legacy branch) — which is evaluated first, and what downlevel step (e.g. esbuild to the canonicalized ceiling) runs after the Svelte compile? Who owns the build command agents run (repo script vs. documented agent-side steps), and how is compiled output verified (ceiling scan + harness) before `add_app`? Resolve inside the Phase 2 evaluation task; do not assume Svelte 5 output is ceiling-safe. The Scribe-engine probe is the deciding evidence, not compiler docs.
6. **Custom Elements: shadow vs light DOM, registration timing, Lit or not.** Which DOM form is viable given the shared `os-*` stylesheet — shadow root (encapsulated, un-themed) or light DOM (themed, unencapsulated)? Does upgrade-on-define paint acceptably on e-ink when the defining script is an appended extra `.js` file, and does `connectedCallback` timing interact with the `DOMContentLoaded` discipline? Is Lit evaluated at all, and if so only after the vanilla pattern proves out? Resolve inside the Phase 2 evaluation task, probe-first on the Scribe engine.
7. **Per-app fallback rules.** When is per-app vendoring (microframeworks) or per-app compilation (Svelte) allowed instead of the shell-provided framework, how is the fallback version pinned and recorded, and who owns its update story? The fallback must never become the undocumented default; resolve inside the Phase 2 tasks and state the rule in the docs.
8. **Versioning and upgrade policy for the provided surface.** How is the provided framework version exposed to bundles, what counts as a breaking change to the provided surface, and what re-verification (reference apps, harness, Scribe probe) is required before a version upgrade ships? Resolve before provision ships; a version upgrade without re-verification must not reach a publish.
9. **Alpine.js specifics.** How does an Alpine-authored bundle bridge to the adapter (per-section store, effect, or `$watch` — and who owns that bridge)? How are `Alpine.data()`/`Alpine.store()` names namespaced by app id, and who owns `Alpine.start()` timing and the `alpine:init` registration discipline? Does expression compilation via `new Function` behave on the JIT-less Scribe engine, and do directive expressions fall under the ES2019 ceiling? Is the shipped size the 7 KB or the ~15–17 KB build, measured on the actual file? Resolve inside the Phase 2 evaluation task, probe-first on the Scribe engine.
