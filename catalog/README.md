# Example apps

Installable reference definitions. Each app is a directory, `catalog/<id>/`, holding `definition.json` (metadata plus a bundle manifest listing the bundle files), the real bundle files (`index.html`, required, plus optional `.js` / `.css`, flat in the directory), and `RECIPE.md` (the install recipe). Each definition installs verbatim via the store path (`install_from_catalog`, which assembles the manifest to the runtime files map) with no shell or package changes. Nothing here seeds automatically: install each app explicitly through `add_app` (hosted MCP path or the `kody dev` local path in `.agents/skills/adding-an-app/SKILL.md`), so every app proves verbatim install.

## Layout

- `catalog.json` — the generated index (see Catalog index below); never hand-edited.
- `<id>/definition.json` — one app definition per directory: metadata plus the bundle manifest (`{ entry: "index.html", files: [...] }`).
- `<id>/index.html` — the required bundle entry, plus any optional `.js` / `.css` bundle files, flat in the directory (only referenced files execute; see the reference contract in `.agents/skills/adding-an-app/SKILL.md`).
- `<id>/RECIPE.md` — that app's install recipe: a procedure of steps, each install step naming exactly one app.
- `tests/` — repo bundle harnesses (plus `tests/read-bundle.cjs`, the shared reader that assembles either definition shape to its files map), not installable definitions.

The Counter bundle is the reference implementation for the bundle/shell interaction contract in `.agents/skills/adding-an-app/SKILL.md` (state-span initial read, shell-form capture/sequencing, single-flight queue, `data-action-base` resolution). Copy its pattern for a new stateful bundle; do not copy its stricter-than-ceiling script style as a rule (see the ceiling note in the Tests section below).

## Apps

Each `<id>/` holds `definition.json` + `RECIPE.md`:

- `app-store/definition.json` — App Store, the browser management surface, as a data app. Stateless, no actions, page only, declaring `capabilities.manageApps`. Its bundle is JS (ES2019, under the 256 KiB cap) that fetches store rows from the shell management API (`GET /manage/rows|install|update|restore`, documented routes, not the bridge) and renders install/update/restore controls from row status, with its own confirmation UI for modified apps and for capability expansion. Decision recorded at implementation (data-only-app-store): the bundle path is documented routes, and the Store is JS-required — without JavaScript it shows a note pointing at agent `add_app`, with no rows. Seeded on the first authenticated shell request against an empty registry, and re-seeded if the registry later becomes empty. Migration note: an already-installed Store from before this change still renders its old static bundle; ask an agent to update it once with `update_from_catalog('app-store')` to get the new Store UI.
- `alembic/definition.json` — Alembic, an e-ink element-combining puzzle (tap only, no drag, no animation). Four recipe sets (the original with nine goals, Little Alchemy, Alchemy Fusion 2, Alchemy by Byril), each saving its own progress through one whole-state `save` action (found ids per set in `p_<set>` string fields, plus `cur`, `sort`, `hints`). The bundle uses KodyBridge v1 with a union-merge rebase, so two devices never lose finds. Larger than most bundles (about 63 KiB, mostly embedded recipe data).
- `counter/definition.json` — unified counter fixture. Retained as the contract fixture: smoke tests, guide, and fast-path verification depend on it. State (`count`) plus `set_count`/`reset_count` actions (effects arrays); the bundle stepper writes through the shared `set_count` action.
- `daily-feed/definition.json` — Daily Feed, a generic agent-pushed daily feed viewer. One state field (`feed`, RSS XML, newest first, at most 14 entries) plus one `set_feed` action; the bundle shows one entry at a time with Previous / Next, and when empty shows a Help-style page with the agent prompt in a code block for the user's agent to start the push. Page only, no live fetch, no copy button.
- `generic-feed/definition.json` — Generic Feed, a generic agent-pushed RSS feed viewer. One state field (`feed`, RSS XML, newest first, at most 14 entries) plus one `set_feed` action; the bundle shows one entry at a time with Previous / Next, and when empty shows a Help-style page with an agent prompt in a code block that leaves a blank for the RSS feed URL — the agent fetches that URL and pushes the feed. Page only, no live fetch, no copy button.
- `eight-ball/definition.json` — Magic 8-Ball bundle. True random shake in-page via vanilla JS with zero navigation; the shake answer persists best-effort through the shared `record_answer` action when reachable.
- `clock/definition.json` — live clock bundle, modal placement (`placements: modal`). Vanilla JS, updates at most once per minute. Opens as a home overlay.
- `calendar/definition.json` — month calendar bundle. Fully JS-driven Sunday-first grid from the device-local date, today highlighted, Prev/Next re-render in place with no navigation, fetch, or act(). Always opens on the current month and keeps no state.
- `news/definition.json` — six-section news bundle. Stateless: World, Technology, Business, Science, Arts, and Finance, each mapped to one declared HTTPS feed (`capabilities.feeds`, 15-minute TTL) read through the shell's feed proxy `GET /feed/news/<name>` and parsed as XML in-page. Masthead, device-local long-form date, section buttons, at most 10 headlines per section with plain-text summaries truncated to 350 characters and a thumbnail only when the feed supplies one; a failed section shows an error state with Retry. Tapping a headline opens the source article in a new tab — the bundle never fetches article content.
- `hoodie-weather/definition.json` — **Hoodie Weather***, next-hour clothing verdict (raincoat / jacket / hoodie / t-shirt). One declared Open-Meteo feed (`capabilities.feeds`, 10-minute TTL) for the default place through the shell's feed proxy, a saved place fetched directly with an honest fallback to the default label plus a notice, a debounced city search against Open-Meteo geocoding, MCP `set_location` (integer microdegrees), a no-argument `restore_default` shell action, and enhance-only `navigator.geolocation` attempted once per load only when nothing is saved. State is just the place (`lat`/`lon`/`label`); the verdict and forecast are derived, never persisted, and nothing polls. When geolocation discovers a place labeled `Current location`, one direct `api.weather.gov/points` request reads `relativeLocation` and persists the city/state as the label (for example `Louisville, CO`); naming is US-only, never supplies or blocks the forecast, and fails silently. The four verdict images are the original HoodieWeather repo PNGs, inlined as data URIs.
- `link-drop/definition.json` — Link Drop, a bookmarklet + agent-prompt link saver. One state field (`links`, array of JSON strings, at most 500 entries, 2048 bytes each) plus `send` (append) and `clear` (set to empty) actions; entries are {t, title, url}, shown most-recent-first as `Title - Date added`, http/https only, all text escaped. In home widgets only the link list shows; the install block and Clear All are page-only. Page placement.
- `xkcd/definition.json` — xkcd comics as a live RSS feed. Fetches through the shell's same-origin feed proxy first (`capabilities.feeds`, 1h TTL), then tries `xkcd.com/rss.xml` directly; shows the comic image with its alt text and falls back to the stored feed when both fetches are blocked. The stored feed starts empty; a live fetch or `set_feed` fills it.
- `arrow-game/definition.json` — Arrow Game bundle. Remove the blue arrows; red arrows are blocked and cost a life, a life every 5 levels, checkpoint fallback. Vanilla ES2019, tap plus best-effort drag, no timer or speed meter. State (board, level, lives, removed) saves through the bridge.
- `cellular-playground/definition.json` — Cellular Playground bundle. Life, Brian's Brain, and Seeds on a 20 by 14 board, step mode plus a slow 500 ms Play timer, dead edges, board as a digit string. Automaton chosen with three buttons; paint Alive / Empty / Refractory (Refractory only for Brian's Brain). The board is one canvas, not per-cell DOM: cells are integer-aligned on a device-pixel-ratio-aware backing store, tap or drag paints through a coordinate hit test, and a focused board supports an arrow-key cursor with Space to paint. Without a 2D context it shows an honest notice instead of a blank board.
- `three-bit-art/definition.json` — 3-Bit Art bundle. 16 by 16 drawing with one Mode button cycling Color, Motif + Color, and Bayer + Color (default Color, saved mode 'pattern' migrates to Motif + Color): Color shows solid 3-bit RGB cube colors; Motif + Color shows eight 16 by 16 motif blocks, each an 8 by 8 tile repeated 2 by 2, one per value, chosen so motif separates the close luma pairs: black solid, blue sparse white dots, red down-right diagonals, magenta down-left diagonals, green horizontal lines, cyan vertical lines, yellow sparse dots, white solid, with the majority area in the original colour and the motif in black or white; Bayer + Color shows 32 by 32 Bayer ordered-dither blocks with the majority pixels in the original colour and the minority pixels in black or white. Gallery of up to 12 drawings, digit-string state. The board is one canvas: each block is built once into an offscreen canvas at the full cell size, where the cell size in device pixels is always a multiple of 32 so one motif pattern pixel is an integer number of device pixels and one Bayer pattern pixel is an integer number of device pixels, cells abut with no gap and no grey between them, tap or drag paints through a coordinate hit test, and a focused board supports an arrow-key cursor with Space to paint. Palette swatches are canvases built directly at a multiple-of-32 device size and gallery thumbnails are small solid-colour canvases. Without a 2D context it shows an honest notice instead of a blank board.
- `probe/definition.json` — Scribe Probe. Capability probe: JavaScript features, storage, and rendering, each result persisted through the shared `append_report` action (reports cap at 1000 since Nov 9, 2026, with a Clear reports action). Phase 2 items (Oct 30, 2026): Proxy, replaceAll, constructable stylesheets / adoptedStyleSheets, custom-element class define + light-DOM render, JSON-seed mount timing, and e-ink re-render cost. BigInt items (Oct 31, 2026) and Wasm items (Oct 31, 2026). Svelte items (Nov 8, 2026): structuredClone (+exec check) and :where() selector support. Perf suite (Nov 9, 2026, catalogVersion 9): the bundle measures navigation timing (`ttfb`, `dcl`, `load`, document KB), resource count/bytes, DOM node count, `performance.memory`, 120-row render and 120-update medians, 30-frame pacing, one app-page GET, and tap-to-frame latency; it auto-runs 0.3 s after load (RUN PERF re-runs) and appends one comma-free `PERF:pb=perf1;ui=shell|spa;...` line to `reports`, so the same bundle compares the original shell and the SPA POC from stored state with no copy/paste on the Scribe. Clipboard write/read test (tap-gated TEST CLIPBOARD button, reported through SEND RESULTS only): on the Scribe `navigator.clipboard` is present but `writeText`/`readText` are denied (`NotAllowedError`), so there is no copy control — prompts stay selectable text.
- `settings/definition.json` — Settings, the browser panel for changing the shell theme and page visibility. Stateless, no actions, page only, declaring `capabilities.theme` with view and set. Reads the settings through `GET /theme/settings` and shows each field's effective value with its source (file default or override); background desk/paper buttons, name text input, icon glyph input with a stock-mark button, per-field reset, and one reset-all button. A Pages section offers Show / Hide and per-field reset for the built-in Help and About pages. Plain GET forms round-trip with a 303 back to the panel; JavaScript enhances in place with `format=json`. A custom grid or custom mark shows a notice instead of an editor.

Rules for all files: one unified shape (meta + `bundle` + `stateSchema` + `set`/`append` actions, optional `capabilities`, no `kind`), ES2019 only (inline scripts and on-disk `.js` alike — the harness scans both), system fonts only, zero emojis, bundle entry carries its `<style>`/`<script>` blocks inline with extra `.js`/`.css` as referenced on-disk files, well under the 256 KiB cap, no external stylesheets or scripts. Shell-rendered UI actions are plain GET forms; bundle in-page buttons additionally write through the same `act()` handler via the GET action URL (`?action=<name>&...&format=json` guarded `fetch` with full-navigation fallback, preserving `k` when present).

Catalog membership checklist: the directory `catalog/<id>/` with `definition.json` + bundle files + `RECIPE.md`, a re-run of the catalog-index generator, and a harness pass (`bun tests/catalog-harness.ts`: validate + install in a blank store + initial state + manifest agreement). Membership is manifest agreement: a definition directory is a catalog app if and only if it has a manifest entry agreeing with it (same id, `catalogVersion`, fingerprint). Extracting bundle files from inline to on-disk form with byte-identical contents needs no `catalogVersion` bump (the assembled fingerprint is unchanged); any other definition change bumps it by exactly 1. Catalog bundles run with session authority: shipping a definition in the catalog is trusting its bundle code, exactly as `add_app` trusts any definition.

## Recipes and install modes

- Default: unattended. A definition with no `installMode` installs from the JSON alone (`installMode: json`); its recipe is the trivial install-and-verify — `install_from_catalog('<id>')`, then verify with `list_apps()`. A definition MAY carry `installMode: "recipe-only"` when its recipe is the only install path.
- `"installMode": "recipe-only"`: the app MUST be installed via its recipe; the Store shows the recipe prompt in place of one-tap install. No current catalog app uses it.
- Only an app with a non-trivial recipe carries `installMode`. Adding the field does NOT bump `catalogVersion`: it is excluded from the definition fingerprint, exactly like `catalogVersion`, so no installed app changes status.
- A recipe is a procedure of steps, each install step naming exactly one app. A recipe installs only its own app: there is no collection recipe, no `collections/` directory, and no `collections` section in the index. Help and About are built-in shell pages with no definition and no recipe.

## Catalog index

The index at `catalog.json` is generated from the app directories by repo tooling — never hand-written. Editing an app's definition or recipe, or adding an app directory, requires re-running the generator from the repo root:

```sh
bun scripts/build-catalog-index.ts
```

Each app entry carries id, label, catalogVersion, fingerprint, installMode, definitionPath, recipePath (paths relative to `catalog/`), and `bundleFiles` (the bundle file paths, sorted, relative to the app directory). The fingerprint is computed by the package's own `fingerprintDefinition` over the assembled definition (manifest resolved to its files map first). The generator writes the manifest only. Regenerating from unchanged inputs is byte-identical; `tests/catalog-harness.ts` fails on a stale index.

The Store lists apps from the `catalog-apps` entry pinned to a line tag, never from `main` directly. The tag is the catalog's id: bare `<major>.<minor>` (for example `4.2`), no patch, no `v` prefix — a patch release cannot change what apps can be installed, so the tag does not need the full version. A shell reads only its own line's tag, so the catalog cannot get ahead of the shell. A repo-added app (or a new version of one) is invisible to the Store until the line tag moves to a commit containing it — committing to `main` alone no longer makes it appear, and no Kody publish is needed for it to appear once the tag moves. The Store's own update is still discovered from `main`, so a new Store version is offered there as soon as it is committed. Local dev never needs a tag: run a tiny static file server on `catalog/` and point `KODY_CATALOG_BASE` at `http://127.0.0.1:<port>/` (loopback http is dev-only; production stays HTTPS-only).

## Pinned catalog maintenance

Adding an app or a new app version moves the line tag — no pin move, no Store update, no version bump anywhere. A tag move is a force-push of one tag by name and needs its own explicit direction naming the tag and the remote, every time:

1. Push the catalog change to `main`, regenerate the index (`bun scripts/build-catalog-index.ts`), and run the harnesses (`bun tests/catalog-harness.ts`, `bun tests/store-harness.ts`, `node catalog/tests/app-store-tests.cjs`). Never move the tag across an unvalidated commit.
2. Move the tag: `git tag -f <major>.<minor> <commit> && git push -f origin <major>.<minor>`. One tag by name, never `--mirror` or `--all`.

A moved tag can serve stale content for a while (`raw.githubusercontent` caches by ref, and a clone that already fetched the old tag keeps the old target until it force-fetches tags) — a new app may take a while to appear. Do not re-move the tag to "fix" a slow appearance; wait for the cache. A bad manifest breaks the listing for the whole line until fixed (manifest validation is all-or-nothing), so the harness run in step 1 is the gate, not an optional check.

When a shell change adds a feature (a minor or major line advance), the old line's tag stops moving — it is frozen at its last commit. Cut the new line tag, move the pin in a new Store version, and publish that Store version to `main`:

1. Cut the new line tag: `git tag <major>.<minor> <commit> && git push origin <major>.<minor>`.
2. Move the pin: in `catalog/app-store/definition.json`, set the `catalog-apps` proxy entry to `https://raw.githubusercontent.com/Hypercubed/kody-os/<major>.<minor>/catalog/`.
3. Bump the Store's `catalogVersion` by exactly 1 (the pin move is a definition change).
4. Regenerate the index and run the harnesses (as above).
5. Commit and push to `main`.

The Store update carrying the new pin is `minPackageVersion`-gated, so a shell older than the new Store's minimum is never offered the update and keeps listing from the frozen tag; after the shell is updated, the Store update goes through and the new catalog is there. Shell first, then Store.

A Store update with the shell unchanged needs no shell change: the Store self-updates from `main` whenever the latest Store version is newer and compatible with the running shell.

Catalog versioning and install snapshots: every catalog definition carries `catalogVersion`, a positive integer starting at 1 on its first versioned release, incremented by exactly 1 on any change to that definition file, never reused, never decreased, never bumped for an unrelated app or a shell change, and distinct from `schemaVersion` and from the package version. A catalog definition without a valid `catalogVersion` fails catalog validation. The canonical stored definition preserves `catalogVersion` through `add_app` normalization. A store install or store update records an install snapshot separate from the definition (install-time `catalogVersion` plus a fingerprint of the canonical stored definition, content only); a snapshot is written only by store install/update (including seeding), never by generic `add_app`/`import_app`, deleted by `remove_app`, and never included in exports. Snapshot-less installs claim no status and get no update control under this scheme. The store never auto-updates. `minPackageVersion` is fingerprinted content, unlike `installMode`: adding or changing it is a definition change requiring `catalogVersion` +1, and `add_app` refuses an app whose minimum is newer than the running shell.

## Install via MCP

Catalog apps install through the store path, which assembles the on-disk manifest to the runtime files map: `install_from_catalog('<id>')` (or the App Store UI), then verify with `list_apps()`. Raw `add_app` transport carries the inline files map only — submitting a manifest-list `definition.json` as-is is rejected, so to `add_app` a catalog app by hand, first assemble it: read `definition.json`, read each file in `bundle.files` from the app directory, and submit with `bundle.files` replaced by the path-to-content map. From a shell with the repo checked out:

```bash
node -e 'var fs=require("fs"); var def=JSON.parse(fs.readFileSync("catalog/counter/definition.json","utf8")); var files={}; def.bundle.files.forEach(function(p){files[p]=fs.readFileSync("catalog/counter/"+p,"utf8")}); def.bundle.files=files; console.log(JSON.stringify({ok:true,id:def.id}));'
```

Then in the agent (Kody MCP), call `add_app` with that assembled definition:

- counter: `add_app(JSON.parse(read catalog/counter/definition.json))` returns `{ ok: true, id: \"counter\" }`.
- eight-ball: `add_app(JSON.parse(read catalog/eight-ball/definition.json))` returns `{ ok: true, id: \"eight-ball\" }`.
- clock: `add_app(JSON.parse(read catalog/clock/definition.json))` returns `{ ok: true, id: \"clock\" }`.
- calendar: `add_app(JSON.parse(read catalog/calendar/definition.json))` returns `{ ok: true, id: \"calendar\" }`.
- xkcd: `add_app(JSON.parse(read catalog/xkcd/definition.json))` returns `{ ok: true, id: \"xkcd\" }`.
- hoodie-weather: `add_app(JSON.parse(read catalog/hoodie-weather/definition.json))` returns `{ ok: true, id: "hoodie-weather" }`.
- arrow-game: `add_app(JSON.parse(read catalog/arrow-game/definition.json))` returns `{ ok: true, id: "arrow-game" }`.
- cellular-playground: `add_app(JSON.parse(read catalog/cellular-playground/definition.json))` returns `{ ok: true, id: "cellular-playground" }`.
- three-bit-art: `add_app(JSON.parse(read catalog/three-bit-art/definition.json))` returns `{ ok: true, id: "three-bit-art" }`.

Re-adding the same id overwrites the definition and preserves state by default (declared fields carried forward, dropped fields reset to `initial`); pass `resetState: true` to restore the legacy wipe, or `migrate` to rename fields. Reference lists (pins, hidden flags, homepage placement, registry order) survive overwrite; only `remove_app` scrubs them.

Verify each install:

1. `list_apps` includes the id.
2. Open `GET /apps/<id>` and confirm it renders.
3. eight-ball: tap Shake, answer updates with no navigation.
4. clock: home tile links to `#app-clock` and the overlay opens with advancing time and no navigation.
5. xkcd: open `GET /apps/xkcd` and confirm the status line reads "Live fetch (proxy)" (or the direct/stored-feed fallback when the proxy is unreachable) and a comic image with its alt text renders.
6. hoodie-weather: open `GET /apps/hoodie-weather` and confirm the default place's label, temperature, conditions, rain chance, and one verdict icon render; use Change place to search and select a city and confirm the label and forecast switch without navigation; then set a US place with `act("hoodie-weather", "set_location", { lat, lon, label: "Current location" })` and confirm the label becomes the NWS city/state (or stays `Current location` if NWS is unavailable), with the forecast unchanged.
7. cellular-playground: open `GET /apps/cellular-playground`, tap or drag a cell, then press Step and Play. The board is a single canvas with crisp integer-aligned cells, and on a canvas-less browser the notice under the board appears instead of a blank area.
8. three-bit-art: open `GET /apps/three-bit-art`, paint in Color mode, tap Mode to cycle through Motif + Color and Bayer + Color and paint again, save to the gallery, then Load and Delete. The board and every thumbnail are canvases, and a canvas-less browser shows the notice under the board.

## Pre-`add_app` authoring checklist

Before calling `add_app` on a new bundle, run the checklist in `.agents/skills/adding-an-app/SKILL.md` (definition validates; bundle renders in `kody dev`; state initializes from the shell span; shell-form actions stay in sync under rapid/overlapping input; ES2019 scan clean; no `window.location.pathname`-only action URLs; stateful bundle follows the interaction contract). ## Tests

`tests/` holds jsdom harnesses for the example bundles — behaviour tests an agent can run without Kody, the hosted OS, or a running `kody dev` server. Nothing in `tests/` is an installable definition. The harnesses read each definition as stored through the shared `tests/read-bundle.cjs` helper (inline map or on-disk manifest, assembled to the same files map). The harnesses today are the counter one, the hoodie-weather one, and the two canvas ones:

- `tests/counter-tests.cjs` — reads `counter/` as stored and checks the definition shape (id, schema version 5, effects arrays, 256 KiB cap, ES2019 ceiling), the stepper's coalesced `set_count` behaviour (rapid clicks, clamp, divergence, fetch failure), and the bundle's sync with the shell: it starts from the shell-rendered `[data-field]` span, keeps that span in sync while stepping, and adopts the shell Reset form's in-place span patch into its display and internal count, including a Reset that lands while a `set_count` is in flight. It also checks the Reset submit itself: the bundle claims it in the capture phase, paints 0 at once, and sends `set_count=0` through the same single-flight queue as the step buttons (so a step taken after Reset, or a stale response landing after Reset, cannot lose or resurrect the old value), with a sequenced fallback for engines that do not deliver submit capture, and that non-Reset forms are not claimed. The harness simulates the shell side with the exact markup `renderAppSection` renders; the server-side `reset_count` action itself is verified through `act()`, not here.

- `tests/hoodie-tests.cjs` — reads `hoodie-weather/` as stored and checks the definition shape (single static HTTPS feed, 600–900 s TTL, `maxBytes` cap, effects arrays, one inline style, ES2019 ceiling), the four-way classifier boundary table (rain 30/31%, apparent 50/51/64/65 °F), next-hour slot selection, the wind-chill fallback, saved-place direct fetch and the honest default-label fallback with Retry, the error state when nothing can be loaded, the claimed `restore_default` shell form through the bridge, debounced city search persisting integer microdegrees, NWS naming of a discovered place (and silent failure, and no naming request for named/default places), and geolocation attempted once per load with silent denial and a stale-response guard.

- `tests/cellular-canvas.cjs` — reads `cellular-playground/` as stored and checks the canvas board: one canvas with no per-cell DOM, a 280-cell grid drawing one rectangle per cell, integer-aligned CSS and backing-store sizes, pointer hit-testing and drag painting, the keyboard cursor, Step advancing the automaton, and the honest fallback when a 2D context is unavailable. jsdom has no canvas implementation, so `getContext` is stubbed with a recording context; that exercises the bundle's own coordinate math and drawing calls, not device rasterization. The Kindle check is the rasterization test.

- `tests/three-bit-canvas.cjs` — reads `three-bit-art/` as stored and checks the same canvas contract for the 16 by 16 art board: one canvas with no per-cell DOM, 256 cells, one Mode button cycling Color, Motif + Color, and Bayer + Color, offscreen motif (16 by 16) and Bayer (32 by 32) colour blocks per value drawn per cell at an integer device-pixel scale with no gap and no grey, solid colors in Color mode, pointer and keyboard painting, palette canvases built at a multiple-of-32 device size, canvas gallery thumbnails with working Load/Delete, old mode 'pattern' migrating to Motif + Color, and the fallback when a 2D context is unavailable. The stub records both `fillRect` and `drawImage`, so tile drawing is checked, not just cell fills.

Run them with jsdom installed ephemerally (no test runner, no `node_modules` in the repo):

```bash
mkdir -p /tmp/jsdom-test && cd /tmp/jsdom-test && npm init -y && npm install jsdom
node catalog/tests/counter-tests.cjs
node catalog/tests/hoodie-tests.cjs
node catalog/tests/cellular-canvas.cjs
node catalog/tests/three-bit-canvas.cjs
```

Ceiling note: the harness checks the Counter bundle's stricter-than-ceiling style (no arrow functions, `const`/`let`, `async`/`await`, or template literals in its script). That style is this bundle's conservative choice, not the binding rule — the binding ceiling is ES2019 and earlier, stated once in `docs/scribe-limitations.md`. Do not reject a new bundle for using `const`, an arrow function, or `async`/`await` alone; reject it for post-ES2019 syntax or APIs.

The live complement to the harness is the `kody dev` end-to-end leg in `.agents/skills/adding-an-app/SKILL.md`: seed the counter fixture through `pkg/scripts/registry.ts`, start `kody dev --target mock`, and check the real shell rendering with `kody dev fetch` (app page markup, action submit, fresh state on reload). The harness simulates the shell-client patch; `kody dev` is the check that the real shell renders the markup the harness assumes.
